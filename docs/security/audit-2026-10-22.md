## Security-relevant change

**`client_guard.py` (new, ~760 lines) — a second, independent layer on top
of the existing commit-message/tracked-term scanners, built to run without
publishing the list it matches against.**

- **Key handling.** The match list is HMAC-SHA256 keyed; the tracked registry
  holds only digests (one per normalized name, one per 4-character prefix, a
  key verifier, and the set of name lengths), never plaintext. The key comes
  from an environment variable or a file under the user's home config
  directory, is read once per process into a local `bytes` value, and is used
  only as the HMAC key for local digest computation and comparison
  (`hmac.compare_digest`) — never written anywhere, never passed to a
  subprocess argument list (`git` calls take no key material; the key is
  consumed entirely in-process), and never included in any printed or raised
  message. A missing or non-matching key raises before any scan content is
  read and exits non-zero (fails closed) — read and confirmed directly in
  `load_key()` and `Registry.verify()`.
- **CI secret handling.** The workflow passes the registry key to the
  scanner only via `env:` (`CLIENT_GUARD_KEY: ${{ secrets.* }}`), never as a
  command-line argument (which would appear in process listings) and never
  echoed or interpolated into a shell string anywhere in the step. GitHub
  Actions' own secret masking additionally hides the literal value in
  logs if it were ever printed, which it is not. `permissions: contents:
  read` and `persist-credentials: false` are both set at job scope.
  Fork-originated pull requests receive no repository secrets under GitHub's
  default behavior (documented accurately in the workflow's own comment);
  the scanner's fail-closed design means every fork PR's check goes red
  regardless of content — an availability/workflow-friction property, not a
  vulnerability, and explicitly accepted by the design.
- **Trusted-copy bootstrapping (new, generic note).** The CI workflow and the
  pre-push hook both prefer the guard and registry committed at a trusted
  revision (the PR base, `origin/main`, or the prior push tip) over the copy
  in the ref under test, specifically so that a change cannot weaken the
  check that judges it by editing the scanner or deleting registry entries.
  Because no commit in this tree yet contains the guard, the workflow's
  documented fallback path (run the copy under test, with an explicit
  `::notice`, only when no trusted copy exists yet) is the path that will
  actually execute on the branch's first push — a one-time, announced
  self-certification until a copy lands on the default branch, after which
  every later change is judged against the version already on the default
  branch. This is inherent to bootstrapping any self-referential check and is
  called out in the workflow's own comments.
- **Local hook is best-effort, not authoritative.** The pre-push layer can be
  bypassed (`--no-verify`, an uninstalled hook, a stale or offline clone) by
  design and by its own comments; the required CI check is the only
  non-bypassable gate, and it runs after the push/PR is already public — the
  workflow's header comment states this distinction ("detects rather than
  prevents") accurately for both layers. The hook's own tests confirm the
  fail-closed properties that do hold locally: a registry present without
  the scanner script blocks the push; a guard reachable at `origin/main`
  overrides a weakened locally checked-out copy; a guard exit code of 2 (no
  key / unreadable registry) blocks the push identically to an exit code of
  1 (a hit).
- **Matching text never leaves the scanner.** Every reporting path
  (`Scanner.report`) emits a rule id and a location string only; in CI mode
  (`withhold=True`) a location that itself contains a registered form is
  replaced with a withheld-location placeholder before being printed, so a
  hit's own file path or branch name cannot leak the registered form into
  public CI logs.
- **Registry file itself.** Read and verified directly: every entry in the
  tracked registry is a 64-character lowercase hex string (schema-checked by
  the loader itself — `Registry.parse` rejects anything else, and rejects an
  empty digest/prefix/length set outright rather than silently reporting a
  clean scan against nothing). No plaintext name, partner identifier, or
  other sensitive value is present in the file. One generic, low-severity
  observation: the registry's `lengths` array is necessarily plaintext (it
  has to be, for the length-indexed matching algorithm to work), so an
  outsider reading the public file learns the count and normalized
  character-lengths of registered forms, though not their content — a
  deliberate, documented design tradeoff, not an oversight.
- **Key-file hardening gap (new, Low).** `load_key()` reads the key from a
  file under the user's home config directory when the environment variable
  is unset, but does not check that file's permission mode before trusting
  its contents. A world- or group-readable key file would be accepted
  silently. Since the key's only secrecy requirement is resisting offline
  dictionary/guessing attacks against the registry's digests (the registry
  itself is already public), this is a hardening gap worth a follow-up
  `stat` check, not an exploitable path by itself.
- **Supply chain / CI config, generic note.** Both the new workflow and the
  pre-existing workflow in this repo pin `actions/checkout` and
  `actions/setup-python` by version tag rather than commit SHA — a
  pre-existing repo-wide convention, not a regression introduced by this
  delta, and not re-litigated further here.

**Test coverage for the above.** `test_client_guard.py` and
`test_install_git_hooks.py` (new/extended) exercise: the full matching-variant
set (case, punctuation, line-wrapped comments, HTML/XML entity and `\u`/`%XX`
decoding, confusable-letter substitution, full-width letters, word-boundary
rules for short names) against synthetic fixture names only (file header says
so explicitly, and this was confirmed by reading the fixtures); key
verification failure paths; a registry with no matching scanner script
blocking the push; the trusted-`origin/main` copy overriding a weakened local
checkout; a new branch being scanned in full rather than based on local
`main`; and the hook refreshing a stale `origin/main` before scanning. All
172 tests in both files pass against the working tree (see Verification).
