## Findings Detail (supporting SEC-12) — in-scope delta only

### RESOLVED — Identity gate could pass every holding when the name oracle returned nothing

**Location:** `skills/parallax-cio-letter-prep/SKILL.md`, Batch A; and the
`analyze_portfolio` row newly added to `parallax-conventions.md` §2.

Before this delta the letter-prep skill fetched ground-truth names with a
single comma-joined `get_company_info` call and cross-validated against a peer
rollup field that `analyze_portfolio` does not return. Both halves failed open.
A comma-joined call fails empty on partial coverage, so one unresolved symbol
left the gate with nothing to compare and every holding passed unflagged; and a
comparison against an absent field can never flag. The delta replaces the
batched call with one call per holding fanned out in parallel, points the
comparison at the per-row `name` fields that the response actually carries, and
adds an explicit UNCHECKED disposition with the rule that a missing comparison
is never treated as a pass — surfaced in the output's coverage-gap section
rather than swallowed. Four other consuming skills received the same repair.
This is the most consequential change in the delta and it strengthens the
repo's central data-integrity control.

### MEDIUM — Contentless names normalize to the empty string and compare equal

**Location:** `skills/_parallax/scripts/contract_validator.py`,
`normalize_company_name()`; rule text in `parallax-conventions.md` §2 step 2.

**Description.** The normalizer case-folds, collapses whitespace, then strips
trailing punctuation and a trailing corporate-form token, repeating until the
string stops changing. A name consisting only of a corporate-form token, or an
absent or whitespace-only name, therefore folds to the empty string.
Independently reproduced: two different contentless inputs both normalize to
`""` and compare equal. A caller implementing the identity check as a plain
equality over normalized names records that as a match — the "missing
comparison treated as a pass" failure arriving through the normalizer rather
than through the lookup.

**Impact.** A holding whose name field is blank or contentless can pass the
identity gate without any real comparison having occurred, which is the
precise failure mode the UNCHECKED rule elsewhere in this delta exists to
prevent. Data-integrity only: it cannot escalate privilege or cross a network
boundary. It is reachable only through absent or contentless input from the
tool response, and the branch's own test confirms no legitimate name in the
tracked fixture is at risk of the collapse.

**Status.** Known and pinned by a test in this delta, which states in terms
that the guard belongs in the normalizer or its callers and that the test file
cannot be the fix. So this is a disclosed residue rather than an unnoticed
hole — but it is unfixed at this pin, and the fix is one guard: treat an empty
normalized form on either side as UNCHECKED, never as a match.

**Remediation.** In `normalize_company_name()`'s callers, or in the function
itself via a distinct sentinel, reject the empty normalized form before
comparing. Mirror the rule into `parallax-conventions.md` §2 step 2 so the
prose gate and the executable gate agree.

**CWE:** CWE-1023 (incomplete comparison logic).

**Post-pin status — REMEDIATED.** Fixed on this branch after `AUDIT_COMMIT`,
so the finding above still describes the state at the pin. `851476c` adds
`names_match()` to `contract_validator.py`, which returns `None` when either
side normalizes to the empty string instead of comparing the folded forms;
`f27f6b5` mirrors the rule into `parallax-conventions.md` §2 step 2, so the
prose gate and the executable gate now agree. Both halves of the Remediation
above are therefore closed. Recorded here rather than by editing the finding
so the audit trail is preserved; the checklist verdicts and the `SUMMARY:`
line remain as evaluated at the pin.

### MEDIUM — The new commit-message gate is documented as running pre-push but is wired nowhere

**Location:** `skills/_parallax/scripts/scan_commit_messages.py`;
`.github/workflows/evals.yml`.

**Description.** The scanner is a correct and well-scoped control, and the
delta's own CI comment states it "runs pre-push" while explaining why it is
deliberately excluded from CI (a shallow checkout has no usable base-ref
range). That reasoning is sound, but the pre-push half does not exist. Grep
across the repo for the script's name finds exactly one reference outside the
script and its own test: the CI comment saying it is not wired there. The
repository's `.git/hooks/pre-push` is the global security-gate wrapper chain,
which does not invoke it. There is no repo-local hook, no installer, and no
`CONTRIBUTING`/`CLAUDE.md` step instructing a contributor to run it.

**Impact.** The control runs only when someone remembers to run it. A pushed
commit message cannot be unpublished, which is the exact property that makes
the manual-only posture weak — and the repo's stated rule about what must not
appear in public commit messages is now partially enforced by an unautomated
step whose documentation implies automation. The gap is a false sense of
coverage more than a live exposure: at this pin the scan was run manually and
the three outgoing messages are clean.

**Remediation.** Either wire the scan into a repo-local pre-push hook chained
ahead of the global gate, or add an explicit "run before every push" line to
`CLAUDE.md` alongside the existing perimeter obligations, and correct the CI
comment so it describes the mechanism that exists. The first is preferable;
the comment fix is required either way.

**CWE:** CWE-1053 (missing documentation-to-implementation consistency);
practically, a gap in A08 software-integrity controls.

**Post-pin status — PARTIALLY REMEDIATED.** `851476c` corrects the CI comment,
which now states plainly that the scan is a manual pre-push step, names the
command, and says no hook invokes it. That is the half the Remediation above
marks as required either way. The other half is still open at HEAD: no
repo-local hook runs the scan and no contributor-facing document instructs
anyone to run it, so the control remains manual-only.

### LOW — CI actions pinned to floating major tags rather than commit SHAs

**Location:** `.github/workflows/evals.yml`.

Third-party actions are referenced by mutable major-version tags rather than
by immutable commit SHA. A compromised or retagged upstream action would
execute in the workflow. Mitigating context is strong and pre-existing: the
workflow declares `permissions: contents: read`, holds no secrets, makes no
live calls, and both actions are first-party GitHub-maintained. Recorded for
completeness under A08, not as an action item for this branch.

### LOW — The generator's `--out` accepts any directory

**Location:** `skills/_parallax/scripts/gen_mock_fixtures.py`, `main()`.

`--write --out <dir>` writes the fixture files into whatever directory the
operator names, with no containment check and no confirmation, and will
overwrite same-named files there. The invoker is the local operator at their
own privilege level and the filenames are module literals, so this is not a
traversal issue; it is noted because the default path is the correct one and
nothing steers a mistyped `--out` back to it.

## Confirmed-sound design points

Checked directly rather than assumed, and recorded so a later audit need not
re-derive them:

1. **The scanner cannot leak through its own output.** `rule_hits()` returns
   `list[str]` of rule ids by construction, with no code path from a match
   object to printed output; the failure message points the reader at a local
   `git show` instead of quoting. Verified by reading every print statement in
   the module.
2. **The scan fails closed on an indeterminate range.** Neither base ref
   resolving raises rather than scanning an empty set, and the exit code (2)
   is distinct from the clean and hit codes.
3. **The generator's randomness is not security-relevant.** A pinned
   xorshift64* generator produces fixture values; it is deterministic on
   purpose, is used for nothing but test data, and no code path uses it where
   an unpredictable value is required.
4. **The seeded generator refuses to emit under an unsatisfied pin.** If the
   pinned seed fails the structural constraints, `main()` returns non-zero
   before writing anything, so a drifting constraint cannot silently produce
   fixtures that satisfy no invariant.
5. **The `NULLABLE` marker tightens rather than loosens the contract
   validator.** It requires the field to be present and permits only null or
   the inner type, and it is explicitly not combinable with the optional
   marker. The alternative — widening the optional marker to admit null —
   would have let a required field disappear entirely without failing.
6. **The plugin mirrors moved with their sources.** Every changed shared
   reference and skill file has its mirror updated in the same commit, and the
   bundle-consistency tests pass, so this delta introduces no distribution
   drift.

## Attacker Perspective (in-scope delta only)

1. Can a tool response shape the identity gate into passing a holding it never
   actually checked? Yes, in one narrow way — a blank or contentless name on
   both sides normalizes to equal (MEDIUM above; remediated post-pin — see the
   Post-pin status note on that finding). Every other path this delta
   touches was tightened: an absent row and a failed oracle call now both
   produce UNCHECKED, and UNCHECKED must be surfaced, not counted as a pass.
2. Can text inside a commit message reach the scanner's output and become
   public through it? No. The output carries rule ids and SHAs only; there is
   no code path from a regex match to a printed string.
3. Can a crafted revision range make `git log` do something other than read
   history? Not through any live path — the range is built from a hard-coded
   base-ref tuple and only the test suite supplies one directly. Worth noting
   for a future change: the range is passed without a `--` separator, so a
   value beginning with a hyphen would be read as an option. Adding the
   separator would make that structurally impossible rather than merely
   unreachable.
4. Can the fixture generator be induced to write outside its directory? Not by
   filename — those are module literals. Only by the operator naming a
   different `--out`, at their own privilege level (LOW above).
5. Does CI hold anything worth stealing? No. Read-only token scope, no
   secrets, no live calls, offline structural checks only.
6. Does the CI term scan running in reduced-strength mode weaken the
   perimeter? It lowers CI to a floor rather than the full gate, which the
   workflow states plainly. The full-strength scan requires a local-only input
   the runner cannot have, and it fails closed without it, so the reduced mode
   is an explicit opt-in rather than a silent degradation. The full scan was
   run at this pin and is clean.
