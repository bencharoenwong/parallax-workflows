## OWASP Findings Detail (supporting SEC-12) — in-scope delta only

**A10 Server-Side Request Forgery — `web_pdf.py` (the primary surface this
re-audit was requested to check):**

- **Resolution and pinning.** `_resolve_public_url` resolves the hostname
  (rejecting literal-IP forms via `ipaddress.ip_address`/`socket.inet_aton`
  first, then `socket.getaddrinfo` for DNS names), and rejects the URL
  outright if *any* resolved address is not globally routable
  (`ipaddress.ip_address(...).is_global`) — a mixed public/private answer
  set fails closed rather than admitting the public member. This is the
  correct DNS-rebinding defense: the socket that actually dials out
  (`_make_pinned_connection`) connects to the pre-validated numeric
  address(es), never re-resolving the hostname at connect time. There is no
  TOCTOU window between validation and connection — the validated IP *is*
  the connect target, by construction, not a second lookup.
- **Multi-address fallback (this delta's change).** Previously only
  `addresses[0]` was pinned; now every validated address is tried in
  resolver order with the last `OSError` re-raised if all fail. This is an
  availability fix (dual-stack hosts), not a security-relevant behavior
  change — every candidate address independently passed the same
  public-only policy before being added to the pinned tuple, so trying more
  of them does not widen the attack surface. Verified by reading
  `_resolve_public_url` end to end and by the new tests
  `test_dial_falls_back_to_the_next_validated_address` and
  `test_dial_reraises_when_every_validated_address_fails`.
- **Redirect handling.** `PublicRedirectHandler.redirect_request` calls the
  stdlib handler to compute the redirect target, then re-runs
  `_resolve_public_url`/pinning on the *new* URL before it is dialed —
  every redirect hop is independently validated and pinned, not just the
  original URL. `_open_public_url` additionally re-validates
  `response.geturl()` after the request completes, as a second check on the
  final settled URL. `test_redirect_to_private_destination_is_rejected_before_body_read`
  (pre-existing, still passing) confirms a redirect to a private destination
  is rejected before any response body is read.
- **`UrlNotPublicError` re-raise (this delta's change).** Before this
  commit, the SSRF rejection inside `extract_from_url`'s inner fetch
  `try/except Exception: pass` was swallowed — the caller never learned
  fetch was blocked, it just silently continued with `raw_html = ""`. That
  was a fail-*open*-looking bug in the calling code even though the guard
  itself was intact (no request was ever actually made to the blocked
  destination — `_open_public_url` still raises before dialing). The fix
  makes the specific exception type propagate to the outer handler, which
  now reports `"error": "URL destination is not public"` distinctly from a
  generic fetch failure. Net effect: strictly more correct signal to the
  caller, no widening of what gets fetched.
- **Entity-unescaping injection check (specifically requested).**
  `_html_to_page_text` strips tags first, then calls `html.unescape()` on
  what remains. Order matters and is correct: unescaping before stripping
  would let an escaped `&lt;script&gt;` in page copy become a live tag for
  the stripper to act on; unescaping after means a decoded `<script>`
  sequence reaches the output as inert text, never as markup the stripper
  interprets. This is proven directly by the new test
  `test_entity_escaped_markup_is_not_revived_into_a_tag`, which asserts the
  literal string `<script>alert(1)</script>` appears in the output *as
  text*. Whether that text is a genuine injection risk downstream depends on
  whether anything later renders it as HTML/DOM or executes it — traced the
  consumers: `page_text` feeds `_voice_corpus_from_text` (word-count/prose
  heuristics) and `merge.py`'s `voice_corpus.text` field, which is not
  referenced by `emit_design_md.py` and is not passed through any
  templating engine (`grep -rn "jinja\|Template(\|render" skills/_parallax/white-label/`
  returns no template usage anywhere in that package). No HTML/DOM rendering
  or code-execution consumer of this text was found in the repo. Conclusion:
  no injection path from the entity-unescape change.

**A08 Software and Data Integrity — audit-chain locking (pre-existing code,
reviewed as requested):**

- **Lock-file permissions.** `view_transaction`'s lock file
  (`.house-view.lock`) is opened with `os.open(..., os.O_CREAT |
  os.O_RDWR, 0o600)` and additionally `chmod`'d to `0o600` after open; the
  containing directory is `chmod`'d to `0o700`. `append_entry` re-applies
  `0o600` to the audit file itself on every append (defense in depth against
  a looser mode from external creation or a prior chmod). This is correct
  for a single-operator local tool.
- **Directory creation/chmod ordering — non-blocking observation.**
  `directory.mkdir(parents=True, exist_ok=True)` runs before
  `os.chmod(directory, _VIEW_DIR_MODE)`, leaving a narrow window where the
  directory carries the process umask's default permissions rather than
  `0700`. In this repo's actual threat model (a Claude Code skill run
  locally by a single operator, no multi-tenant server, no privilege
  boundary between the code and its caller) this is not exploitable: an
  attacker able to race that window already has the same filesystem access
  as the process creating the directory. Noted for completeness, not scored
  as a finding, because it does not cross a real privilege boundary in how
  this repo is used.
- **Symlink/TOCTOU on the lock path.** `os.open` does not pass
  `O_NOFOLLOW`, so a pre-planted symlink at the lock path would be followed.
  Same reasoning as above: exploiting this requires write access to a
  `0700` directory the attacker doesn't otherwise have, which is not a
  meaningful escalation in a single-user local-tool context. Flagged for
  awareness, not a finding.
- **Hash-chain tamper-evidence.** `verify_chain` walks the log line by line,
  recomputing `compute_entry_hash` (SHA-256 over `rfc8785`-canonicalized
  JSON) on each entry and comparing it to the next entry's
  `prev_entry_hash`; a single `chain_root` is enforced (a second one raises
  `AuditChainBroken`), and a missing `prev_entry_hash` inside an
  already-chained section also raises. This logic is unchanged by the
  in-scope delta (see Scope Note — only `ViewChangedMidRun` and
  `identity_diff` are new here) and reads correctly: any single-byte
  tamper to a historical entry changes its hash, which no longer matches
  the *next* entry's stored `prev_entry_hash`, breaking verification from
  that point forward. `append_entry`'s race-free `O_CREAT|O_RDWR` open
  (no truncate) plus `fcntl.flock(LOCK_EX)` around the read-tail/compute/write
  cycle prevents the two-concurrent-first-writer truncation race the code
  comment documents as the reason for that pattern.
- **New logic in this delta (`ViewChangedMidRun`, `identity_diff`).** Both
  are pure, I/O-free functions: `identity_diff` does a dict-key
  comparison and string-formats the diff; `ViewChangedMidRun` is an
  exception type with no behavior. No new attack surface. Their effect
  (deduplicating the compare-and-format logic previously implemented twice,
  once in `judge.py` and once in `stress.py`) is a correctness/maintenance
  improvement — the two race guards can no longer silently drift apart in
  which fields they compare.

**Attacker Perspective (in-scope delta only):**

1. Could the multi-address SSRF fallback be tricked into dialing a private
   address by first returning a public IP and then, on retry, a private
   one? No — `_resolve_public_url` rejects the entire address set up front
   if *any* member is non-public; the fallback only iterates over addresses
   that individually already passed that check. There is no code path where
   `_make_pinned_connection` is given an address that was not pre-validated.
2. Could a malicious page's HTML entities be crafted to re-form a tag after
   unescaping and reach a rendering context? No renderer/templating consumer
   of `page_text`/`voice_corpus.text` exists in the repo (checked above);
   the extracted text is inert data (JSON/Markdown fields), and the explicit
   regression test confirms the escaped sequence is decoded to *text*, not
   re-parsed as markup, by the extractor itself.
3. Could the `UrlNotPublicError` re-raise fix regress into now dialing a
   destination it previously skipped? No — the change only affects whether
   the *caller* is told the fetch was blocked; the underlying guard
   (`_resolve_public_url`/`_open_public_url` raising before any socket is
   opened) is unchanged and unconditional regardless of how the caller
   handles the exception.
4. Could an attacker use `runrecord.py`'s unreachable status to sneak
   changes past review under the assumption "nobody runs this"? Reviewed on
   the assumption it *will* be wired in eventually: no injection, path
   traversal (beyond an already-trusted caller-supplied path), or unbounded
   resource-consumption issue was found in the dataclass/JSON-parsing logic
   itself.
