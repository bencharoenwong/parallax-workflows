## Findings Detail (supporting SEC-12) — in-scope delta only

### HIGH — Unbounded local file read via `write[...].path` refs, resolved before commit validation — **RESOLVED at `2bc98ad`**

**Location:** `skills/_parallax/house-view/view_commit.py`, `_resolve_content()`
(the function backing `build_commit_args()`, called from `main()` before
`commit_view()`).

**Description.** A commit plan's `write` values may be either
`{"inline": "..."}` (literal text) or `{"path": "..."}` (a filesystem
reference). For a `path` ref, `_resolve_content` does:

```
source = Path(ref["path"]).expanduser().resolve()
if source.parent == Path(view_dir).resolve():
    raise CommitRejected(...)
return source.read_text(encoding="utf-8")
```

The only containment check is "the resolved parent is not the view
directory itself" — a footgun guard against silently reading the file about
to be replaced, not a security boundary. There is no allowlist directory,
no restriction to a designated staging path, and `resolve()` follows
symlinks, so the check cannot be strengthened by symlink tricks either way
— it is simply absent. Any path readable by the local user's account (SSH
keys, cloud-credential files, other users' exported documents, `/etc/*`)
can be named in a `path` ref and its bytes copied into `view.yaml`,
`prose.md`, or `provenance.yaml`.

**Why this matters for this pipeline specifically.** The task brief
describes the plan JSON as arriving on stdin "from an LLM-composed
source" — in practice, the operator LLM (running `parallax-load-house-view`)
composing the CLI invocation after extracting a CIO document (PDF/text/
URL) that this feature exists to ingest. This repo's own prior audit
already treats content harvested from such documents as adversarial: the
`download_public_url`/`_resolve_public_url` SSRF fix exists precisely
because "logo/favicon URLs are harvested from untrusted page content." The
same reasoning applies here one level up the chain — a document engineered
to prompt-inject the operator LLM into emitting a `path` ref for a
sensitive local file would have that file's contents committed into
`prose.md` or `view.yaml`: artifacts explicitly built and retained as a
7-year, tamper-evident compliance record, and later handled by
`audit_export.py` for bundling to external auditors. That is a materially
worse destination for an accidental secret than a transient log line.

**Why HIGH and not CRITICAL.** Exploitation requires an intermediate step
(the operator LLM must be induced to emit the malicious `path` value; this
is not a directly network-reachable read), and the read stays within the
local user's own filesystem permissions — no privilege escalation, no
cross-tenant exposure, no network trust boundary crossed. It is not scored
as a SEC-12 FAIL (which requires ≥1 Critical finding) for that reason, but
it is a real, currently-unmitigated confused-deputy primitive that lands
in a long-retention artifact rather than a transient one.

**A read also happens before any write-path validation runs.** `main()`
calls `build_commit_args()` (which resolves every `path` ref) before
`commit_view()` (which runs the token/whitelist/identity/row-vs-bytes
checks). A plan that is ultimately rejected — wrong mode, missing identity
keys, disallowed artifact name — has still caused the filesystem reads for
every `path` ref it named. Nothing is written to disk in that case (the
CLI's exit-2 contract holds), but bytes from an arbitrary path are loaded
into process memory, and there is no size cap on that read distinct from
the `os.O_EXCL` staging path's own protections. This is a secondary,
lower-severity aggravation of the same root cause, not a separate
exploitation path.

**Recommendation:** restrict `path` refs to a designated staging directory
(an explicit env var or a fixed subdirectory such as
`~/.parallax/active-house-view/.staging/`), reject any resolved path
outside it before reading, and defer the read until after
`validate_write_remove_keys`/`validate_audit_entry` have passed so a
doomed-to-be-rejected plan cannot cause an out-of-scope read at all.
Suggested handoff: `refactorer` for the code change; a corresponding
`test_view_commit.py` case asserting a `path` outside the staging
allowlist is rejected without being read.

**RESOLUTION (`5cf42c8..2bc98ad`).** The recommendation above is implemented
essentially as written: a `--staging-dir` argument plus a `resolve_staging_dir`
helper now require every `path` ref to resolve to a file whose parent equals
one declared, bounded directory, checked before any read, with a fail-closed
default when no staging directory is declared. Verified directly (not just by
reading the diff) via the attack attempts logged in the Second Pass section
above: `..` traversal, an in-staging symlink resolving outward, and the
no-staging-dir case are each rejected before any file is opened, both through
the internal functions and through the real CLI end-to-end. The specific
attack this finding described -- an LLM-composed plan naming an arbitrary
absolute or relative path -- is closed. One narrower bypass survives; see the
new finding immediately below, which is a distinct, smaller gap in the same
mechanism rather than a reopening of this one.

### MEDIUM — A hard link placed inside the declared staging directory reaches `provenance.yaml`, which has no content validation

**Location:** `skills/_parallax/house-view/view_commit.py`, `_resolve_content`
(the staging-directory containment check) and `_validate_row_matches_bytes`
(the row-vs-bytes check that follows it).

**Description.** The containment check compares `source.parent` -- the
resolved parent directory of the `path` ref -- against the resolved staging
directory. `resolve()` follows symlinks, which is exactly what defeats a
symlink placed inside the staging directory pointing elsewhere (verified
above). A hard link is not a symlink: it is a second directory entry for the
same underlying file, indistinguishable from an ordinary file by `resolve()`,
`is_file()`, or any check in this function. A hard link created inside the
staging directory, targeting a file's content anywhere else on the same
volume, satisfies every check in `_resolve_content` -- its resolved parent
literally *is* the staging directory -- and its bytes are read in full.

For `view.yaml` and `prose.md`, this is caught one step later, by pre-existing
validation unrelated to this delta: `_validate_row_matches_bytes` requires
`view.yaml`'s bytes to parse as a YAML mapping matching the audit row's
`view_hash`, and requires `prose.md`'s bytes to carry frontmatter whose
`prose_body_hash` matches its own body -- checks an arbitrary local file's raw
content will not coincidentally satisfy. **`provenance.yaml` has no equivalent
check.** `_validate_row_matches_bytes` only inspects the `"view.yaml"` and
`"prose.md"` keys of the write set; `provenance.yaml` is accepted verbatim.

**Demonstrated, not just reasoned about.** Built a full plan with valid
`view.yaml` and correctly-hashed `prose.md` staged normally, and a
`provenance.yaml` write ref pointing at a hard link (created inside the
declared staging directory, targeting an unrelated file elsewhere on the same
volume) placed at the `provenance.yaml` slot. Ran the real
`python3 -m view_commit --mode save --staging-dir <staging>` CLI end-to-end
against a scratch view directory: it exited 0, printed a normal committed
audit row, and the target file's full byte content was present verbatim in
the resulting `provenance.yaml` on disk -- a complete, successful commit, not
a partial or rejected one.

**Why MEDIUM and not HIGH.** Unlike the resolved finding above, this cannot be
triggered by a `path` string alone. Creating a hard link is a distinct
filesystem-write action that must happen inside the staging directory before
the commit runs -- something with write access to that specific directory
(and read access to the target, on this platform) has to execute it, which is
one concrete step heavier than composing JSON text. It also stays within the
same local-account trust boundary as every other finding in this delta: no
privilege escalation, no cross-tenant exposure, no network trust boundary
crossed. It is downgraded from the resolved finding's HIGH rating specifically
because of that extra required capability, not because the resulting read is
any less unbounded once it happens.

**Recommendation:** extend the existing containment check to reject a `path`
ref whose target has more than one hard link (`os.stat(...).st_nlink > 1` on
POSIX, checked at the same point symlinks are already implicitly rejected --
before the read), or, more directly, give `provenance.yaml` the same
bytes-level validation `view.yaml` and `prose.md` already have so that no
write slot is exempt from a content check. Suggested handoff: `refactorer`
for the code change; a corresponding `test_view_commit.py` case placing a hard
link inside the staging directory targeting `provenance.yaml` and asserting
rejection.

**Note (not scored, not independently reproduced):** `_resolve_content` also
calls `resolve()`, then `is_file()`, then `read_text()` as three separate
filesystem operations rather than one open-and-check. This leaves a
theoretical TOCTOU window -- a concurrent process could swap the staging
directory's entry between the parent-equality check and the final read. Not
attempted here (reliably winning that race is a separate exercise from
demonstrating the hard-link bypass above, and the required capability --
a second process racing writes into the same staging directory during a
single synchronous CLI invocation -- already implies at least as much local
capability as the hard-link bypass) and not scored as a finding; recorded as a
residual worth a one-line mention if the hard-link fix above touches this
function anyway.

### MEDIUM — `TransactionToken` is a proof-of-lock object only against duck-typed impostors, not against direct construction

**Location:** `skills/_parallax/house-view/audit_chain.py` (`TransactionToken`
definition) and `view_commit.py::commit_view_locked` (the `isinstance`
check).

**Description.** `commit_view_locked` requires
`isinstance(token, audit_chain.TransactionToken) and token.view_dir == view_dir`.
The new test suite (`test_impostor_tokens_are_rejected`) confirms a
duck-typed stand-in — a same-named `namedtuple` or a bare `object()` — is
correctly rejected, because `isinstance` checks the concrete class, not
structural shape. But `TransactionToken` is a plain, publicly importable,
frozen `@dataclass` with no private constructor gating and no linkage to
the actual held file descriptor. Any caller can do
`audit_chain.TransactionToken(view_dir=some_path)` directly and pass the
result to `commit_view_locked` — it satisfies both the `isinstance` check
and the `view_dir` equality check without ever having called
`view_transaction()` or holding `.house-view.lock`. Separately, because the
token is immutable and carries no reference to lock liveness, a token
retained past the `with view_transaction(...):` block that minted it
remains "valid" by this check even after the flock has been released —
a genuine replay gap, not just a forgery gap.

**Why this is not exploitable today.** `commit_view_locked` has exactly one
call site in the shipped code: `commit_view()`, which acquires the token
from `view_transaction()` and passes it to `commit_view_locked()` within
the same `with` block, in the same function, before the lock can be
released. No other code — including `main()` — calls `commit_view_locked`
directly. So today, forging or replaying a token requires writing new code
that misuses the API; it cannot be triggered by a malicious plan on stdin
or by any existing call path.

**Why this matters going forward.** `DECISIONS.md`'s own flip conditions
for this branch name the scenario that would make this reachable: "a
second non-CLI caller needs the already-locked variant (e.g. a future
maker path that must commit inside a transaction it also uses for
something else)." The maker.py migration is explicitly deferred, not
abandoned, and `commit_view_locked` is the documented entry point for it.
The moment a second caller exists, a token minted for one purpose (or
constructed directly, bypassing `view_transaction` altogether) could be
handed to `commit_view_locked` outside the lock's actual hold, silently
defeating the mutual-exclusion guarantee the whole module exists to
provide, with no error raised.

**Recommendation:** before the deferred maker migration lands, bind the
token to proof of a currently-held lock rather than to a value comparison
— e.g., store the lock file's file descriptor (or `id()` of the open file
object) on the token at mint time and re-verify with an `fcntl` state
check (or a monotonically increasing per-process nonce compared against a
live registry) at `commit_view_locked` entry, so a bare
`TransactionToken(view_dir=...)` construction cannot pass and a token
cannot outlive the `with` block that minted it. Until then, this is a
design gap worth tracking rather than an active vulnerability — recommend
a one-line `DECISIONS.md`/module-docstring note that `commit_view_locked`
must only ever be called with a token from a `with` block still on the
stack, so the constraint is explicit for whoever writes the maker
migration.

### MEDIUM — Fixed heredoc delimiters in newly-added `SKILL.md` bash templates can collide with document-derived free text

**Location:** `skills/parallax-load-house-view/SKILL.md`, all of the new
`python3 -m view_commit --mode ... <<'PLAN' ... PLAN` and
`python3 -c '...' <<'ROW' ... ROW` invocation templates (Step 3b, Step 4
Stage 2, and the `--extend`/`--re-pair`/`--clear` sections).

**Description.** Every new invocation template in this rewrite uses a
fixed, predictable heredoc terminator (`PLAN` or `ROW`) with the JSON
payload's field values filled in by whichever LLM is executing the skill.
The design correctly keeps the largest untrusted payload — the prose body
and view/provenance YAML content — out of the heredoc entirely, passed
instead by file `path` reference and read by `view_commit`'s own Python
code. But several fields that are inlined directly into the JSON text
inside the heredoc are plausibly document- or operator-influenced free
text: Step 3b's `hint` (explicitly "the hint text truncated to 200 chars,"
sourced from re-extraction guidance that may quote source-document
content) and `query_summary` (a source file basename or URL — filenames on
POSIX may contain embedded newlines, and a crafted URL fetched from
adversarial content is a channel already treated as untrusted elsewhere in
this repo), and `--clear`'s `reason` field. If any such value contains a
line matching the literal delimiter (`ROW` or `PLAN` alone on a line), bash
heredoc parsing terminates early: the JSON payload is truncated, and
whatever text follows the fake terminator in the composed command is
interpreted as ordinary shell input by the same script that is about to
run with the operator's privileges.

**Why MEDIUM and not HIGH/CRITICAL.** This is a prose-only construct — no
code in this delta implements or executes it; its risk is entirely a
function of how faithfully the executing LLM instantiates the template
from the SKILL.md example. It is bounded to commands run locally with
authority the operator's own agent session already has (this is the same
"no privilege boundary between code and operator" trust model the rest of
this branch's documentation already accepts for its concurrency guards).
It is flagged because the brief explicitly names this rewrite as an
"enforcement surface [with] nothing test[ing] its contents," and this is a
concrete, structural way that surface can misfire independent of operator
intent.

**Recommendation:** avoid inlining any document- or operator-derived free
text field into a heredoc body at all — write every such value to a file
(the same `path`-ref mechanism `view_commit` already supports and that
Step 4 Stage 2 already uses correctly for the three body artifacts) and
reference it, or generate the JSON payload programmatically and pipe it in
rather than hand-composing a heredoc literal. If a heredoc literal is kept
for the short, structurally-bounded fields (ids, hashes, timestamps),
prefer a randomized per-invocation delimiter over a fixed word. This is a
documentation change, not a code change, and out of scope for this
docs-only audit to apply directly.

## Confirmed-sound design points (priority areas from the task brief)

Recorded because the brief asked these to be explicitly judged, not just
implicitly passed over:

- **Validation ordering** in `commit_view_locked` matches the documented
  contract exactly: token identity → `validate_write_remove_keys` (key
  whitelist) → `validate_audit_entry` (audit-entry shape) →
  `_check_identity` (identity guard) → `_validate_row_matches_bytes`
  (row-vs-bytes) → `_stage_and_rename` → `remove` loop → `append_entry`.
  Confirmed by reading the function top-to-bottom and cross-checking
  against `test_view_commit.py`'s ordering-sensitive tests (e.g.
  `test_moved_identity_writes_nothing`, `test_row_that_disagrees_with_bytes_is_rejected`).
- **The artifact-name whitelist and its path-traversal guards** are sound:
  `audit.jsonl` is rejected by literal name before any other check runs;
  `/`, `\`, `..`, and `.tmp.` substrings in an artifact key are rejected
  even though today's three `WRITABLE` names could never contain them —
  explicitly kept as defense-in-depth against a careless future extension
  of `WRITABLE`, per the code comment, and this reasoning holds up.
- **The `version_id` path guard** (used to build the `<name>.tmp.<version_id>`
  staging filename) correctly rejects `/`, `\`, `..`, and leading/trailing
  whitespace in the raw `version_id` string. Checked whether the
  *concatenated* filename could contain `..` even when `version_id` alone
  does not (e.g. `version_id="."` yielding `...tmp..`) — confirmed this
  does not constitute traversal: two dots inside a single path component
  is not a parent-directory reference on POSIX, only an exact `..`
  component or a `../` sequence is, and both remain excluded.
- **Staging via `O_CREAT|O_EXCL|O_WRONLY` at `0600` with `fsync` before
  rename** is implemented as described and covered by
  `test_staged_files_are_created_0600_not_chmodded_after` — no
  world-readable window under a permissive umask.
- **The error taxonomy and its CLI exit-code mapping** hold up:
  `CommitRejected`/`ViewChangedMidRun` → exit 2 ("nothing was written"),
  everything else (`CommitPartiallyApplied`, `CommitWitnessLost`, and any
  unexpected exception) → exit 1. `test_cli_partial_apply_does_not_exit_2`
  and the explicit `assert not issubclass(CommitPartiallyApplied, CommitRejected)`
  pin this at the type level, not just by test observation of a single
  code path.
- **The identity resolvers** (priority area 4): confirmed `view_hash` and
  `prose_body_hash` both recompute from on-disk bytes
  (`compute_view_hash(_load_view(view_dir))`,
  `compute_prose_body_hash(path.read_text(...))`) rather than reading
