## OWASP Findings Detail (supporting SEC-12) — in-scope delta only

**A10 Server-Side Request Forgery — `download_public_url()` (new this delta,
the primary surface this audit was requested to check):**

- **Routes through the same policy as the page fetch, including redirects.**
  `download_public_url` opens the request via `_open_public_url`, the exact
  function `extract_from_url`'s page fetch and the stylesheet-follow path
  already use: non-HTTP(S) schemes and non-public destinations are rejected
  before any socket opens, the TCP dial is pinned to the pre-validated
  numeric address (no re-resolution at connect time), and each redirect hop
  is independently re-validated/re-pinned before its body is read
  (`PublicRedirectHandler.redirect_request` re-runs the destination check on
  every `newurl`; `_open_public_url` re-checks `response.geturl()` after the
  request completes as a second check on the settled URL). Confirmed by
  reading the call chain end to end and by the new
  `TestAssetDownloadDestinationPolicy` test class, including
  `test_redirect_to_private_destination_leaves_no_partial_asset` (asserts
  zero body reads and no file written when the *final*, post-redirect,
  destination is private).
- **Size limit.** `response.read(max_bytes + 1)` bounds the read itself
  (not a post-hoc check on an unbounded buffer); a payload over `max_bytes`
  (default 5 MB, matching `LogoValidator.MAX_FILE_SIZE`) raises before
  anything is written to disk. Verified directly and by
  `test_oversized_asset_is_rejected_before_it_reaches_disk`.
- **No partial asset on rejection.** The full validated payload is held in
  memory before `destination.parent.mkdir` / `destination.write_bytes` run;
  a destination-policy rejection, a redirect-to-private rejection, or an
  oversized response all raise before any filesystem write. Confirmed by the
  three negative tests in the same class (`assert not dest.exists()` in
  each).
- **Destination-path handling — no traversal in the one real call site, but
  the function provides no destination confinement of its own.** The only
  caller in this repo (`skills/parallax-white-label-onboard/references/workflow-code.md`
  Step 4b, which is agent-followed guidance rather than code executed
  automatically at skill-invocation time) builds `dest` as
  `f"{assets_dir}/logo-primary{ext}"`, where `ext` is
  `Path(urlparse(url).path).suffix` — the file-extension text after the last
  literal `.` in the URL's final path segment, taken from untrusted page
  content (a harvested logo URL). I tested this adversarially: a URL path
  containing `../../etc/...`, encoded `%2f`/`%2e` sequences, or extra path
  segments cannot make `ext` contain a literal `/` character (Path-based
  suffix extraction only looks within the final path segment, and percent
  sequences are never decoded by this code path), so `ext` cannot escape
  `assets_dir` through this call site — confirmed by direct testing, not
  assumed. That said, `download_public_url` itself does not validate or
  confine `dest` in any way: it is a general "write this validated
  download to this caller-given path" primitive that trusts the caller
  completely for the destination. If a future call site ever derives `dest`
  from untrusted content more directly than an isolated extension suffix,
  this function would not catch it. Recorded as a non-blocking design note,
  not a finding against the current, single call site.
- **Overwrite and symlink-follow — non-blocking, matches the existing
  local-tool threat model.** `destination.write_bytes(payload)` uses the
  default open mode: it silently overwrites an existing file at `dest`
  (expected — "fetch the current logo") and would follow a pre-existing
  symlink at that path rather than refusing to. Exploiting the symlink case
  requires an attacker to already have write access to
  `~/.parallax/client-branding/assets/` before the download runs, which is
  the same trust boundary the prior audit already assessed as
  non-exploitable for this single-operator local-tool repo (no privilege
  boundary between the code and its caller). Same reasoning applies here;
  not scored as a finding.
- **Content-type handling — the new function does not check it; a
  pre-existing downstream check partially covers the gap.** Unlike
  `_fetch_external_stylesheets` (which inspects `Content-Type` and skips
  non-CSS/text responses), `download_public_url` writes whatever bytes come
  back regardless of `Content-Type`. In the one real call site, the written
  file is subsequently passed to `LogoValidator.validate_logo` (pre-existing,
  unchanged by this delta), which rejects content that fails to parse as an
  image via PIL for every supported format except SVG (SVG's dimension
  check is skipped entirely) — so a non-image response saved under a
  `.png`/`.ico` name would generally fail that later check, except (a) when
  PIL is not installed, where the validator returns `pass` with dimensions
  unchecked, and (b) for SVG specifically. This downstream behavior was read
  but not exercised end-to-end this session (see Scope Note). Recorded as a
  non-blocking observation, not scored against this delta, since
  content-type filtering was not part of what this commit changed or
  claimed to add.

**A02 Cryptographic Failures / sensitive-data-persistence — `_scrub_query`
rewrite (this delta's second web_pdf.py change):**

- **The replacement is complete for query-string values**, verified by
  reading the code and by adversarial testing beyond the shipped test suite
  (repeated keys, malformed percent-encoding, a legacy semicolon-delimited
  pair, embedded control characters, double-encoded values, and non-`str`
  input) — every case redacts fully or is rejected outright
  (`bytes`/`None` input → the literal `"(invalid URL)"` marker, never a
  partially-serialized value). The bare-segment case
  (`?<opaque-token>`, no `=`) is dropped in its entirety, key included,
  because a blank-valued pair cannot be distinguished from an opaque token
  used as the key — confirmed both by the shipped
  `test_sanitized_url_drops_bare_query_segments` and by direct testing.
  This closes the exact defect the commit describes: the prior denylist
  (introduced earlier in this same delta by `8877c1a`, then replaced here)
  matched on parameter *name*, and named a fixed list of secret-looking
  keys — any value under an unlisted key name (OAuth `code`, `jwt`,
  `nonce`, and unboundedly many more) passed through unredacted. The
  current version inspects no key names at all: every value is replaced,
  full stop.
- **Residual, out-of-scope gap: the URL PATH is not touched by this fix and
  never has been.** `_sanitized_url` reconstructs the persisted reference
  from `scheme`, `host`(+port), `path` (verbatim, unmodified), and the
  scrubbed query — the `path` component was never redacted, before or after
  this commit (confirmed: `parsed.path` is passed through unchanged in both
  the pre-`3b77ec6` version and the current one). A token embedded directly
  in the URL path rather than the query string — e.g. a magic-link or
  password-reset URL of the form `/reset-password/<token>` — survives into
  `source.reference` verbatim, unaffected by this fix. This is a real,
  reproducible gap (confirmed by direct testing this session), but it is
  not a regression and not part of what this commit's docstring or commit
  message claims to fix — both explicitly scope the guarantee to "the
  query's shape" / "every query value." Flagged here because the task
  explicitly asked whether the replacement is complete for "any value" —
  it is complete for the class of leak this commit set out to close
  (query-string values), and it is not a general guarantee against every
  way a URL can carry a secret. Recommend a follow-up to scope-check
  path segments the same way, tracked separately rather than folded into
  this delta's PASS.
- **Persistence sink confirmed.** `source.reference` (the output of
  `_sanitized_url`) is written by `build_config_from_draft` into
  `~/.parallax/client-branding/` per the function's own docstring and the
  existing `loader.py` wiring (unchanged by this delta) — read to confirm
  the threat model claim in the commit message is accurate, not assumed.

**A08 Software and Data Integrity — `ViewChangedMidRun` guard in
`maker.py` (new this delta):**

- **Cannot be bypassed by the described race.** `save_view` acquires
  `audit_chain.view_transaction`'s exclusive `flock` *before* calling
  `_save_view_locked`, which re-reads the active view's parent version from
  disk and compares it (via `identity_diff`, unchanged pure-diff helper
  reviewed in the prior audit) against the value captured at synthesis time
  — i.e. before the interactive confirmation gate that can sit open
  indefinitely. Every writer that touches this view directory in this repo
  (`maker.py`, `stress.py`, `judge.py`) acquires the same lock before
  writing, so by the time the re-read runs inside the lock it observes
  the true latest committed state — no writer can be "mid-write" while this
  check runs, and no writer can commit between the re-read and this
  function's own writes, because both happen under the same held lock.
  Traced all three lock call sites; there is no fourth writer.
- **Abort leaves no partial write.** The guard raises
  `audit_chain.ViewChangedMidRun` before `view_dir.mkdir` and well before
  any of the four artifact writes (`view.yaml`, `prose.md`,
  `provenance.yaml`, `audit.jsonl`) later in the same function. The
  exception propagates out through `view_transaction`'s
  `try/finally: fcntl.flock(...LOCK_UN)`, so the lock is always released
  even on abort — verified by reading `view_transaction`'s
  context-manager structure directly (`@contextmanager` wrapping a
  `try/finally` around the `yield`), not merely by the passing test suite.
  Confirmed by the two new tests: `audit.jsonl` is byte-identical
  before/after a rejected save, and `verify_chain` still passes afterward
  in both the direct-rejection test and the "a real writer lands during the
  gate" test.
- **No type-confusion bypass.** Both sides of the comparison pass through
  `str(...)` identically (including the `None`-parent case, which becomes
  the literal string `"None"` on both sides), so there is no mismatched
  representation an attacker-controlled draft could exploit to make a
  genuinely-moved parent compare equal.
- **Threat model scope.** This guard protects against benign concurrent
  writers (another maker run, a judge/stress apply) racing the interactive
  gate — a real correctness bug this delta fixes — not against an
  adversarial caller deliberately forging a matching `parent_version_id` in
  its own draft dict to evade the check. This repo has no
  privilege boundary between the code and the operator invoking it, so that
  is not treated as a bypass in this repo's threat model, consistent with
  how the prior audit assessed the lock file's other properties.

**A03 Injection — `evals/graders/infra_failure.py`,
`evals/graders/runrecord.py` (JSON-parsing hardening, this delta):**

- Both files parse already-on-disk transcript JSON via `json.loads` with
  dict `.get()` access and defaults; this delta adds `isinstance(event, dict)`
  / `isinstance(message, dict)` / `isinstance(usage, dict)` guards before
  calling `.get()` on a JSON value that parsed successfully but is not a
  dict (a JSON array, string, or number at the top level of a line, or
  nested under `message`/`usage`) — previously this would raise
  `AttributeError` and crash the grader on a malformed or adversarially
  crafted transcript line rather than skip it cleanly. No `eval`/`exec`, no
  shell invocation, no dynamic import, no path construction from transcript
  content anywhere in either file. `runrecord.py` additionally has no
  import site in the repo outside its own tests (see above) — assessed as
  inert code on that basis, not as active runtime surface, per the task's
  instruction.
- The `infra_failure.py` regex change (`401(?!\d)` in place of `401`) is a
  correctness fix (a 4-plus-digit status code no longer false-matches the
  401 substring) with no ReDoS exposure — a single-character negative
  lookahead does not introduce backtracking.

**Attacker Perspective (in-scope delta only):**

1. Could a malicious page's harvested logo URL be crafted to write outside
   `~/.parallax/client-branding/assets/`? No — tested directly; the
   extension-only `dest` construction in the one real call site cannot
   contain a literal path separator regardless of encoding tricks in the
   source URL's path.
2. Could a query-string secret survive redaction through some encoding
   trick the shipped tests don't cover? No — tested repeated keys,
   malformed percent-encoding, a semicolon-delimited legacy pair, embedded
   control characters, double-encoding, and non-`str` input; every case
   redacts the value fully or rejects the whole URL. A secret embedded in
   the URL *path* rather than the query string does survive — a real,
   pre-existing, out-of-scope gap, not a bypass of this commit's specific
   claim (see A02 detail above).
3. Could the `ViewChangedMidRun` guard be raced by a second writer landing
   between the re-read and the actual file writes? No — both happen inside
   the same held `flock`, and every writer in this repo acquires that same
   lock before writing.
4. Could an attacker use `download_public_url`'s lack of its own
   content-type check to plant an arbitrary file type under a trusted-looking
   name in the assets directory? Partially mitigated, not fully closed: the
   downstream `LogoValidator` catches most non-image content for
   PIL-checked formats, but not when PIL is unavailable or for SVG. Recorded
   as a non-blocking observation above, not exercised end-to-end this
   session.
