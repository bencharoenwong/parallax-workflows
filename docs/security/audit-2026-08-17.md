## Detailed review — `install_git_hooks.sh`

Read in full. Design intent is stated in the script's own header: an earlier
version inserted the guard by searching for the hook's last `exit ` and
writing above it, and that search was wrong in five independent ways (matched
inside a conditional branch that does not always run; missed a bare `exit`
with no trailing space; never reached anything after a hook ending in
`exec`; discarded the original hook's exit status when appending; did not
tilde-expand a `core.hooksPath` of `~/hooks`). The current design prepends
the layer immediately after the shebang instead, which removes that whole
class of failure by construction: the layer is always the first executable
statement, and the original hook body runs after it with its own exit status
intact. Each of the five shapes has a dedicated regression test, and each
test runs the installed hook rather than reading its text — the guard has to
execute and block, not merely be present in the file.

Refusals reviewed and confirmed correct: a symlinked `pre-push` file is
refused rather than edited or followed (would otherwise detach the clone from
a managed source or mutate a shared target); a hook whose first line is not a
recognized shell shebang is refused rather than corrupted; a `core.hooksPath`
that resolves outside the repository is refused unless
`PARALLAX_HOOKS_FORCE=1` is set explicitly, because such a path is shared by
every clone pointed at it and editing it is a global change dressed as a
per-repo install — the force override affects only this one refusal, not the
symlink or non-shell-hook checks. The outside-repo comparison resolves both
the hooks directory and the repo root through `realpath` (falling back to a
Python equivalent, then to the unresolved path if neither is available)
before the prefix comparison, which closes a gap the script's own comments
flag: an unresolved string-prefix test would have let a *symlinked* hooks
directory pointing outside the repo pass the check and be written through.
A dedicated test plants that symlink and confirms the refusal fires, then
confirms the force override still reaches the shared target when intended.

Failure handling reviewed: on a hook write, the previous hook (if any) is
backed up before modification; a post-write `bash -n` syntax check and a
reachability assertion (the marker must appear before the file's first
top-level `exit`/`exec`, proving the layer is not merely present but is on
every execution path) both restore the backup on failure rather than leaving
a broken or silently-inert hook in place. The idempotency check matches the
marker only as an installed comment block (`^# --- marker (BLOCKING)`), not
as a bare substring, so a stray mention of the marker text in an unrelated
comment cannot cause the installer to falsely report "already installed" and
skip repairing a broken install — verified by a dedicated test.

No shell-injection, path-traversal, or privilege-escalation issue was found.
All paths handled (`$ROOT`, `$HOOKS_DIR`, `$HOOK`) are quoted throughout; none
are built from user-supplied or push-time-attacker-influenced input — they
come from `git rev-parse` and the local repository layout only.

## Detailed review — the installed pre-push layer

Read in full, both as static text and as executed by the test suite's
`_hook_blocks()` / stdin-driven harness. It runs `python3` against
`skills/_parallax/scripts/scan_commit_messages.py`, resolved via
`git rev-parse --show-toplevel` at push time rather than a path baked in at
install time — reviewed and confirmed intentional and correctly scoped, see
Findings below for the one caveat this creates. It reads the ref list git
supplies on stdin (`local_ref local_sha remote_ref remote_sha` per line),
builds a revision range per ref, and blocks the push on any non-zero exit
from the scanner (both a hit, exit 1, and an unresolvable range, exit 2, are
treated as blocking — the scanner's own fail-closed design is honored rather
than only its clean/hit distinction). Because the layer is prepended and
consumes stdin to compute the range, it captures the ref list to a temp file
and re-points stdin (`exec <`) before returning control to the rest of the
hook; a dedicated test confirms a downstream hook stage still receives the
full, un-drained ref list rather than an empty one. An all-zero local sha
(branch deletion) is recognized and skipped rather than passed to `git log`
as a bogus range. Invoked by hand with no ref list on stdin (a deletion-only
push, or a manual run), it falls back to the scanner's own default range
rather than silently skipping — so it can never pass vacuously.

The range string passed to the scanner is built only from SHA hex digits
supplied by git itself (`<remote_sha>..<local_sha>`, or the bare local sha
for a new branch); it cannot begin with a hyphen and so cannot be
misinterpreted as an option by the scanner's argument parsing. This differs
from the residual noted in the prior audit for the *manual* invocation path,
where an operator-supplied range could in principle start with `-`; that
residual is unaffected by, and unrelated to, this hook-supplied path.

### Confirming the task's stated prior assessment

The layer executes whatever `scan_commit_messages.py` is on disk in the
current working tree at push time — not a copy pinned to the commit(s) being
pushed. A prior review judged this not a meaningful escalation over running
any cloned repo's tooling, because installing the hook is an explicit
opt-in step and execution still requires the user to push, at their own
privileges. **Confirmed**, with one property stated plainly rather than left
implicit: installing the hook converts a script that would otherwise need a
deliberate per-run invocation into one that runs automatically on every
future push for as long as the hook stays installed, using whatever copy of
the script is checked out at that moment — not the copy associated with
whichever branch is actually being pushed, if the two differ (an edge case:
ordinary `git push <remote> <local-branch>` pushes the branch that is
checked out, so the two normally coincide). That standing-execution property
is not unique to this installer; it is the property every git hook manager
(this pattern, `pre-commit`, `husky`, and similar) accepts as the cost of
automating a check the user would otherwise forget to run by hand, which is
the documented motivation for this hook in the first place. No new trust
boundary is crossed: same user, same privileges, no network fetch, no
content sourced from anywhere but the already-checked-out working tree.

## Findings Detail (supporting SEC-12) — in-scope delta only

### LOW — `CLAUDE.md` describes the installer's superseded insertion mechanism

**Location:** `CLAUDE.md`, "Run the commit-message scan before every push"
paragraph.

**Description.** The line reads: "... backs up any existing hook and
inserts the layer *before* the hook's final `exit`, since appending to a
hook that ends in `exit 0` leaves the guard unreachable." That is the exact
design the installer's own header comment says was replaced: searching for
and inserting above a hook's last `exit` was wrong in five independent ways
(a match inside a conditional branch that does not always run; a bare
`exit` with no trailing space that the search missed entirely; a hook ending
in `exec`, which the search cannot anchor on at all; a discarded original
exit status; an unexpanded `~` in `core.hooksPath`). Commit `23941d2` added
this `CLAUDE.md` line describing that design; a later commit on this branch,
`7cf6757`, replaced the actual mechanism with prepend-immediately-after-the-
shebang and added the regression tests for all five broken shapes, but did
not update this line. Verified directly by reading both commits and by
reading the shipped script, which prepends after the shebang (see Detailed
review above) — not before a trailing `exit`.

**Impact.** Documentation-only. The operative instruction — run the
installer — is correct, and 17 passing tests confirm the actual mechanism
works. The risk is a future maintainer reasoning about *how* the layer is
placed from this line (for example, assuming their own hook customization
placed after the layer's insertion point would run before it) and being
wrong, or distrusting the installer if they read the source and find the
description does not match. No exploitability: nothing about the scanner's
actual placement or execution depends on this text.

**Remediation.** Update the parenthetical to describe prepend-after-shebang,
matching the installer's own header comment.

**CWE:** CWE-1053 (missing documentation-to-implementation consistency),
same category as a finding recorded in the prior audit.

## Confirmed-sound design points

Checked directly rather than assumed, and recorded so a later audit need not
re-derive them:

1. **The reachability assertion is a real check, not a restatement of
   `bash -n`.** It asserts the marker line's position precedes the file's
   first top-level `exit`/`exec`, which is what defeated all five of the
   originally-broken shapes; every one of those shapes passes `bash -n`
   while failing this assertion, and the test suite proves each one is
   caught.
2. **The stdin re-pointing does not silently break downstream hook logic.**
   A dedicated test writes a second hook stage that counts the ref lines it
   receives and confirms it sees the full list, not an empty one drained by
   the prepended layer's own `while read`.
3. **The force override is scoped to exactly one refusal.**
   `PARALLAX_HOOKS_FORCE=1` bypasses only the outside-repo-hooksPath
   warning; the symlinked-hook-file refusal and the non-shell-hook refusal
   are unconditional and have no override, confirmed by reading every use of
   the variable in the script (there is exactly one).
4. **The scanner invoked by the layer is unchanged from the prior pin's
   review.** `subprocess.run(["git", "-C", str(repo), *args])` remains
   list-form with `shell=False`; the layer's own `python3 "$_PARALLAX_SCAN"
   "$_PARALLAX_RANGE"` call is likewise argv-form with no shell
   interpolation, and the range string is built only from git-supplied hex
   SHAs (see Detailed review above).

## Attacker Perspective (in-scope delta only)

1. Can a malicious commit that modifies `scan_commit_messages.py` reach
   execution without the user choosing to run it? Only by first being
   checked out into the working tree by some other action (a `git checkout`
   or merge the user already performed) and then surviving until the next
   `git push` — the layer runs whatever is on disk at push time, not a
   pinned or fetched copy. It cannot fetch or execute anything the user has
   not already brought into the working tree by their own action. See the
   "Confirming the task's stated prior assessment" section above.
2. Can a crafted push (attacker-controlled remote or ref names) make the
   layer's `git log` invocation or the scanner's argument parsing do
   something other than read history? No — the range passed is built only
   from SHA hex digits git itself reports, never from ref *names*, and
   cannot begin with a hyphen.
3. Can the installer be tricked into writing through a symlink, or into a
   shared out-of-repo hooks directory, without the operator intending it?
   No — both are refused by default, verified by dedicated tests including
   one where the symlink is planted before the install runs.
4. Does the installer or the layer hold or transmit any credential? No —
   neither reads, writes, nor logs any secret-shaped value; the only
   environment variable read is a non-secret local opt-in flag.
