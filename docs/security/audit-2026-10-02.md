**Targeted probes run today, beyond the standard sweep:**

- **Untrusted-JSON handling in `translation_validate.read_document`.**
  `object_pairs_hook` rejects duplicate keys (`ValueError`), `parse_constant`
  rejects `NaN`/`Infinity`/`-Infinity`, `parse_float` rejects non-finite
  floats — all three correctly folded into the function's `except (OSError,
  UnicodeError, ValueError)` handler and reported as a `[FATAL]` line, exit
  code 1. Deeply nested JSON is a gap: `RecursionError` is not a subclass of
  any caught exception, so it propagates as an unhandled traceback rather
  than a clean `[FATAL]` line. Measured on the pinned gate interpreter
  (`python@3.11` 3.11.11): a same-key object nested ~1,000 levels deep raises
  `RecursionError` (matches 3.11's default `sys.getrecursionlimit()`);
  depths of 500 and 900 still parse successfully. The failure **is fail-closed**
  in effect — the process exits 1 either way, and no partial/incorrect pass
  result is produced — but it leaks a local file-path-bearing traceback to
  stderr instead of a controlled message. This is a local CLI tool with no
  HTTP response surface, so it is not an SEC-08 (response hygiene) issue;
  recorded as a code-quality/robustness finding under SEC-12. Recommend
  adding `RecursionError` to the caught-exception tuple.
- **Regex complexity in the shared validator.** `NUMBER`, the `_units`
  composite, the currency alternation, and the Vietnamese "tỷ"/"đồng"
  unit-compound lookarounds were each timed against adversarial inputs up to
  ~1.28M characters (long digit runs, ambiguous separators, repeated
  magnitude words) — all scale linearly. One regex in `PROTECTED` does not:
  its email-address alternative (`\b[\w.+-]+@[\w.-]+\.[A-Za-z]{2,}\b`)
  exhibits classic quadratic backtracking on a long, space-free run of
  word/`.`/`-`/`+` characters with no `@` in it (e.g. a long dotted-decimal
  or hyphenated run). Measured: n=2,000 chars → 0.12s, n=4,000 → 0.46s,
  n=8,000 → 1.84s, n=16,000 → 7.4s, n=32,000 → 32.4s (clean ~4x-per-2x-input
  scaling = O(n²)); isolating just that alternative reproduces the same
  curve, and removing it from the alternation drops the same inputs to
  single-digit milliseconds. The trigger requires the run to contain no
  whitespace: the same character count broken into ordinary space-separated
  tokens (`'1.1 ' * n`) stays linear (0.004s–0.016s up to n=32,000), so
  ordinary prose, numbered lists, and version strings with normal spacing do
  not trigger it — a deliberately crafted long unbroken token is needed.
  `PROTECTED` is reached only via `fidelity()`, i.e. only when a skill is
  invoked with `--source` (full fidelity check); `--style-only` never calls
  it. Impact is CPU time on the operator's own local process; there is no
  network-facing endpoint behind this code, consistent with the SEC-06 NA
  below. Recommend bounding the quantifiers to realistic email lengths
  (e.g. `[\w.+-]{1,64}@[\w.-]{1,253}`) or a possessive quantifier (supported
  on this repo's Python baseline, 3.11+); a file-size cap in
  `read_document` would add defense in depth. Not Critical (no attacker-
  reachable network boundary), but a real algorithmic-complexity bug (CWE-1333)
  worth fixing before any future network-facing use of this validator.
- **`html.parser.HTMLParser` complexity under the pinned gate interpreter.**
  `_Markup` (built on `HTMLParser`, `convert_charrefs=False`) is exercised on
  both source and translated text in `fidelity()`. Timed an ambiguous-entity
  adversarial input (`"&amp" * n`, no terminating `;`) on
  `/usr/local/opt/python@3.11/bin/python3.11` (3.11.11, the gate's pinned
  interpreter) versus the system's current Python (3.14.0). On 3.11.11,
  time-per-character rises with input size (n=160,000→0.361s, 320,000→0.640s,
  640,000→1.82s, 1,280,000→5.47s — i.e. per-char cost roughly doubles as `n`
  grows 8x, a superlinear trend), while the same inputs on 3.14.0 hold a flat
  per-character cost across the same range (1,280,000 chars → 2.27s, same
  ratio as the smallest case). This is consistent with the task's description
  of a 2025 CPython performance fix to `html.parser` not being present in the
  pinned 3.11.11 build. Same reachability caveat as above: only via
  `--source` mode, local CLI, no network boundary. Recommend tracking a
  python@3.11 patch bump and re-measuring; not a blocking finding today.
- **`importlib` dynamic loading in the four per-language wrappers.** Each
  wrapper resolves exactly two fixed candidate paths —
  `Path(__file__).with_name("translation_common.py")` (same directory, for a
  vendored `.skill` package) and `Path(__file__).resolve().parents[2] /
  "_parallax" / "translation_validate.py"` (fixed relative offset, for the
  repo/plugin tree) — and loads whichever exists via
  `importlib.util.spec_from_file_location`. Neither candidate is built from
  an environment variable, CLI argument, or any other caller-supplied value;
  there is no way to make this loader import a file outside the skill tree.
  Unchanged risk profile from how `bootstrap_manifest.py` loads
  `render_gate.py` in the prior audit (fixed, repo-local path).
- **`subprocess`/shell use in packaging.** `build_bundle.py`'s one
  `subprocess.run` call (`git ls-files`, list-argument form) takes a
  `rel_prefix` built from internal registry/manifest entries, never raw CLI
  text passed through to a shell. `skills/build-skills.sh` (`set -euo
  pipefail`) uses no `eval`/`os.system`-equivalent and no shell-string

  arguments, used only in quoted contexts. No new `shell=True`, `eval(`,
  `os.system(`, `pickle`, or `yaml.load`-family call introduced anywhere in
  this delta.

## Remediation after AUDIT_COMMIT

Applied on the same branch, after the audited commit; verdicts above describe the audited commit.

- Protected-token email pattern: quantifiers bounded to realistic lengths. Measured on the pinned 3.11.11 interpreter: a 32,000-character dotted run now scans in milliseconds.
- Deeply nested JSON: `RecursionError` is caught and reported as a `[FATAL]` message.
- Found during remediation, not in the checklist pass above: the magnitude-unit scan was also quadratic on long digit runs (a 32,000-character `1,1,1,...` run took about 200 seconds). It now finds each number once and tests for a unit where it ends; the ticker pattern is length-bounded. The worst of eight adversarial 32,000-character inputs now takes about 0.3 seconds.
- Also found during remediation: the copied-prose check and the no-translate block search could rescan the input on adversarial text (many unclosed start markers). The copied-prose pattern starts matches only where no letter precedes, and blocks are now found with a linear marker search.
- Not remediated: `html.parser` superlinear scaling on the pinned 3.11.11 interpreter. The fix is in later CPython releases; upgrading the gate interpreter resolves it. Reachable only through the local `--source` CLI.

Regression tests for each item are in `skills/_parallax/test_translation_validation.py`.
