**Code-level review of `release.py` (new file), focused on its two
security-relevant surfaces — archive extraction and release-integrity
verification:**

- `unpack()` (`skills/_parallax/scripts/release.py:99`) rejects absolute
  paths, `..` segments, backslashes, drive-letter colons, symlink entries,
  and non-regular/non-directory member types before writing, and
  normalizes (NFC + casefold) each member name to catch case- or
  Unicode-form duplicate members that would collide on a case-insensitive
  filesystem (this duplicate-member check is the fix landed in the
  audited commit itself, confirmed by the 3rd-party commit title). A
  pre-extraction check caps any archive at 5,000 members / 200 MB
  declared expanded size.
  **Tested empirically** (not just read): built a 2 MB payload archive,
  then hand-patched its central-directory "uncompressed size" field down
  to 10 bytes to see whether a forged small declared size lets an
  oversized payload slip past the 200 MB pre-check. It does not —
  Python's `zipfile` validates CRC-32 against the actual decompressed
  bytes on `read()` independent of the declared size field, and raised
  `BadZipFile` before any bytes were written to disk. `release.py`'s own
  `main()` (`release.py:947`) catches `zipfile.BadZipFile` and fails
  closed with a printed error. **Not a finding** — recorded here because
  it was a plausible bypass worth testing, not because it is one.
- `verify_release()` (`release.py:305`) checks `path.is_symlink()` for
  every entry in `index["assets"]` (`release.py:316`) before hashing, but
  does **not** apply the same symlink check to `index.json`
  (`release.py:308`, read via `.read_text()`) or `SHA256SUMS`
  (`release.py:332`, read via `.read_text()`) before reading them. If the
  directory being verified is itself attacker-influenced (not the case in
  the documented maintainer workflow, which verifies a directory it just
  built — `docs/releases.md` "Check and build" — but is possible if a
  user ever points `release.py verify` at an untrusted downloaded
  directory), a symlinked `index.json`/`SHA256SUMS` would be read through
  silently instead of rejected like the asset files are. **Low severity,
  non-blocking**: no code execution path, worst case is reading an
  unexpected local file's bytes into the comparison, and the documented
  workflow treats this tool as a self-check on the maintainer's own build
  output rather than a trust boundary for third-party downloads.
- `digest()` (`release.py:49`) reads an entire file into memory
  (`path.read_bytes()`) before hashing, with no file-size cap at the call
  sites in `verify_release` for `index.json`/`SHA256SUMS` specifically
  (the `.zip`/`.skill` assets it's also called on are already
  size-capped by `unpack`'s pre-check during `verify_asset`). **Low
  severity, non-blocking**: same attacker-model caveat as above; this is
  memory use, not a corruption or execution path.
- Supply-chain/integrity controls reviewed and confirmed present:
  checksummed, atomically-exposed build output (staged in a temp
  sibling directory, `verify_release()` run against the staging dir
  before `assets.rename(output)`, `release.py:895`); source-tree
  fingerprinting that re-checks after build and refuses to expose output
  if the source changed mid-build (`release.py:891`); a hard requirement
  for a clean, committed tree and a matching CHANGELOG heading before any
  non-preview build (`release.py:834-837`); MCP URL validation that
  requires `https`, a non-empty host, and no embedded credentials in the
  URL (`release.py:740-744`); every `subprocess`/`git` invocation in this
  file uses list-argument form with no `shell=True` and no untrusted
  string ever reaches a shell.
- `distribution_docs.py` only reads the skill manifest already present in
  the repo and rewrites README text between two marker pairs, raising
  `BuildError` if either marker pair is missing or duplicated
  (`distribution_docs.py:455`); no new external input surface.

## Critical Findings Detail

None at Critical, High, or Medium severity. Two Low-severity,
non-blocking observations (both in `skills/_parallax/scripts/release.py`,
new in this diff):

1. **Symlink check asymmetry in `verify_release`** (CWE-61-adjacent,
   informational). `path.is_symlink()` is checked for every entry in
   `index["assets"]` (`release.py:316`) before hashing/reading, but
   `index.json` (`release.py:308`) and `SHA256SUMS` (`release.py:332`)
   are read via `.read_text()` with no equivalent check. Only matters if
   a user ever points `release.py verify` at a directory they did not
   just build themselves — the documented workflow
   (`docs/releases.md` § "Check and build") always verifies a
   just-built, trusted staging directory. Remediation: add the same
   `is_symlink()` guard before reading either file.
2. **Unbounded read in `digest()` for non-archive files**
   (`release.py:49`, called at `release.py:308`/`332` context via
   `.read_text()` which has the same unbounded-read shape). No file-size
   cap applies to `index.json`/`SHA256SUMS` the way `unpack()`'s
   5,000-file/200 MB check bounds the `.zip`/`.skill` assets. Same
   attacker-model caveat as above — local self-verification tool, not a
   network boundary. Remediation: apply a sane size cap (e.g. a few MB)
   before reading either file, consistent with the archive-asset path.

Neither finding changes the SEC-12 PASS verdict (no Critical finding);
both are recorded for the maintainer's backlog, not gate-blocking.
