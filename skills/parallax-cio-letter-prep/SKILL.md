# CIO Letter Prep Pack

## When not to use

- Single stock analysis → use /parallax-should-i-buy or /parallax-deep-dive
- Daily fund manager brief → use /parallax-morning-brief
- RIA / wealth-advisor client review → use /parallax-client-review
- Reactive drawdown attribution after a single event → use /parallax-explain-portfolio
- Backtesting a strategy (not covered by Parallax workflows)
- Period start more than 365 days before today → export_price_series trailing-window cannot reach it; split into quarterly windows or adjust start date

## Gotchas

- JIT-load `_parallax/parallax-conventions.md` for RIC, symbol cross-validation, parallel exec, fallbacks, news async, macro reasoning, and disclaimer
- JIT-load `_parallax/house-view/loader.md` ONLY if `house_view` is supplied AND forward-outlook will render. House view is scoped to the forward-outlook section ONLY — retrospective sections (header, attribution, contributors, detractors, trade narrative, macro, news) are always view-agnostic. No view → omit forward-outlook entirely; never retrofit view language onto retrospective prose.
- Attribution method is "daily contribution analysis" (NOT "time-weighted" / TWR — that's a different industry term for return calculation, and conflating them confuses practitioners). Math: `scripts/contribution.py` replicates the server's own method — each holding compounds daily (buy-and-hold, weights drift) between rebalances; on a rebalance date the day's return applies to the pre-rebalance value first, then the book reweights to the new target (trade after close). Per-holding contribution is that holding's dollar P&L; the portfolio total is `final_value/initial_value − 1`. Naive `weight × period_return` is silently wrong when positions change mid-period, and so is a plain arithmetic sum of `daily_weight × daily_return` — that was this skill's own earlier (now-fixed) bug.
- **`company_contribution[].contribution_pct` is a return contribution, NOT a P&L share.** The identity is `contribution_pct == row.total_pl / portfolio_parameters.initial_value`; equivalently, the rows sum to `portfolio_summary.total_return` (the always-available form of the check — `portfolio_parameters.initial_value` is schema-optional). A value of 0.00215 means "this holding contributed ~21.5 bps of the period's return" — read it directly. `contrib_bps = contribution_pct × 10000`. No multiplication by `total_return` — that would scale every figure by the period's own return and corrupt the numbers. (An older server build returned a P&L-share basis that summed to 1.0 and needed a `× total_return` conversion; see the runtime guard below — the skill must not assume the current basis without checking.)
- **Rank and split sign directly from `contribution_pct`; do not re-derive it.** Under the current return-contribution basis the sign is already correct per holding — a losing holding has negative `contribution_pct`, a winning holding positive, independent of the portfolio's overall sign. Do not multiply by `total_return` to "fix" the sign; that was only ever needed under the retired P&L-share basis, where a row's sign is the holding's sign *times* the portfolio's sign, not the holding's own: in a losing period a losing holding reads positive (negative ÷ negative) and a winning holding reads negative — applying that correction now, when the basis is already return-contribution, flips every sign in a losing period instead of fixing one.
- **Runtime basis guard (cheap, no extra call).** Before converting or ranking, compute `s = sum(contribution_pct)` over `company_contribution[]`. If `s` is close to `portfolio_summary.total_return` (within ~1 bp, i.e. 1e-4 — loose enough to absorb per-row 6-decimal rounding over a large book), the endpoint is on the current return-contribution basis — use `contribution_pct` as-is. If instead `s` is close to `1.0`, the endpoint has reverted to the retired P&L-share basis — apply `contrib_bps = contribution_pct × total_return × 10000`, take the sign from the converted value (under the share basis, raw `contribution_pct`'s sign is `sign(holding total_pl) × sign(portfolio total_pl)`, not the holding's own sign — e.g. in a losing period a losing holding reads positive and a winning holding reads negative; only the converted value isolates the holding's own sign), and note "legacy P&L-share basis detected, converted" in About This Report. If neither match, halt rendering with the diff — the basis is unknown and the numbers cannot be trusted. Apply the same check to `sector_contribution[]`, which follows the same basis as `company_contribution[]`.
- **Server-side numbers are canonical.** `analyze_portfolio.company_contribution` produces the LP-facing numbers; `scripts/contribution.py` is the local reconciliation audit, but it is only an EXACT gate on a **single-currency book** (owner decision, 2026-10-07): every holding listed in the portfolio's base currency, operationally `portfolio_summary.total_fx_pl == 0`. On a single-currency book, `contribution.py` now replicates the server's own compounding/rebalancing method (see Math Reference), so there is no arithmetic-vs-geometric gap and no rebalance-date convention skew left to absorb — the residual 25-bp tolerance covers data differences only (vendor-reported cash dividends vs the dividend-event feed `get_stock_outlook` reads, and the calendar-fill convention on a date either side is missing its own close), and a divergence outside that band on a single-currency book IS a real bug in inputs, prices, dividends, or trade log — halt rendering with an audit-failed error. **On a multi-currency book, local-vs-server is NOT an exact gate.** The server's `total_price_pl` carries an FX-weight-drift cross term (`price_pl = starting_value_base × changepercent`, and the server's own BASE-currency weights drift with FX as well as with price) that this module has no way to replicate — it has no currency-conversion step and no FX data at all. A local-vs-server gap on a multi-currency book is reported as **INFORMATIONAL**, with a one-line FX explanation, and NEVER halts rendering on its own. Multi-currency books are NOT left unaudited, though: the three server-internal-consistency checks below (company/sector `total_pl` sums; `total_pl / initial_value == total_return`) still run and still halt on failure, on every book regardless of currency — they catch server-side data corruption independently of the FX gap this skill cannot close.
- `scripts/contribution.py` enforces a 1-bp inner reconciliation gate (`|sum(contributions) − portfolio_total_return| > 1bp` → `ReconciliationError`). On gate fire, surface the diff and abort. Never catch-and-discard.
- **Reconciliation gates on the server's total-return-before-FX field, `total_price_pl` — exactly, on a single-currency book; informationally, on a multi-currency book.** Live verification (single-holding VZ.N book, 2026-10-06) established that `total_price_pl` — like `price_pl`, `total_pl`, `total_return`, and `CHANGEPERCENT` — is a TOTAL-RETURN field: the server adds the cash dividend back on the ex-date and carries it forward (compounded), and the ONLY component it isolates separately is FX (`total_fx_pl` plus a price x FX cross term) **on a single-currency book**. On a multi-currency book, the server's base-currency weights ALSO drift with FX, which introduces the FX-weight-drift cross term documented in the Gotcha above — `total_price_pl` there is not cleanly "dividends in, FX out" the way it is for a single-currency book. **The earlier assumption that `total_price_pl` was price-only (no dividends) was wrong** — correct it everywhere in this document and in `scripts/contribution.py`. `scripts/contribution.py` works from `export_price_series` prices (raw, price-return closes — no dividend adjustment) in each holding's own listing currency, plus the per-holding `dividend_schedule` built in Batch A from `get_stock_outlook(aspect="dividends")` (see Step 2 and Math Reference), and has no currency-conversion step. With `dividend_schedule` supplied, its output is a total return before FX: dividends included, FX excluded — the same basis `total_price_pl` reports on a single-currency book. Compare against `total_price_pl`, not `total_return`/`total_pl`, which also carry FX:
  - **Classify the book first.** `is_single_currency = (portfolio_summary.total_fx_pl == 0)` (within the same rounding budget as the reconciliation check itself, i.e. treat a `total_fx_pl` under ~$0.01 per $10,000 of `initial_value` as 0). If `total_fx_pl` is ABSENT from the response (an older server build), fall back to: single-currency if every holding's `get_company_info.currency` (or `.data.currency` on the nested shape) equals `portfolio_parameters.base_currency` (requested in scope by Step 2's `fields=` list). If `base_currency` is ALSO absent, or any holding's currency cannot be resolved, do not guess and do not PASS — the classification itself is `UNVERIFIED` per conventions §4.0: report the local-vs-server comparison as unverified/informational (never a halt on this specific comparison, same as the multi-currency path) and say why in About This Report.
  - `server_total_return_before_fx = portfolio_summary.total_price_pl / portfolio_parameters.initial_value`. `total_price_pl` is already in scope from Step 2's `fields=` list, which now also requests `portfolio_parameters` directly, so `initial_value` is normally available without any derivation. As a fallback only (e.g. an older server build that omits the field despite being requested): if `initial_value` is absent, derive it as `portfolio_summary.final_value − portfolio_summary.total_pl` (exact for this skill's calls, which leave `include_transaction_costs` at its default of `false`); if `final_value` is also absent, derive it as `portfolio_summary.total_pl / portfolio_summary.total_return` (guard against `total_return == 0`). If none of these resolve `initial_value`, halt with "cannot compute server total-return-before-FX (initial_value unresolved)" — do NOT fall back to comparing against `total_return`, which mixes in FX local math cannot see; that is exactly the masking failure mode this gate exists to prevent.
  - **Single-currency:** if `|local − server_total_return_before_fx| ≤ 25 bps`: **PASS, total return before FX** — render server-side numbers as usual, note in About This Report that FX is not modeled by the local audit (dividends ARE modeled, via `dividend_schedule`), and report the FX-only residual in bps as `(portfolio_summary.total_pl − portfolio_summary.total_price_pl) / portfolio_parameters.initial_value × 10000` (this residual is `total_fx_pl` plus a price×FX cross term ONLY — it is NOT a dividend residual, since `total_price_pl` already includes dividends; it collapses toward 0 only when the book has no FX exposure — which is already true by the single-currency classification, so this residual should itself be ~0). If `> 25 bps`, it's a real divergence independent of FX — **halt** as usual.
  - **Multi-currency:** regardless of the size of `|local − server_total_return_before_fx|`, this comparison is **INFORMATIONAL ONLY and never halts rendering** — the local math is FX-free by construction and cannot be expected to match a server figure carrying an FX-weight-drift cross term it has no visibility into. Report it in About This Report as `Reconciliation audit: INFORMATIONAL (multi-currency) — local total-return-before-FX {X} bps vs server {Y} bps; diff {Z} bps not evaluated against the 25-bp gate — local math has no FX-weight-drift term (see Gotcha)`. The server-internal-consistency checks below are what actually gates a multi-currency book.
  - **Server internal-consistency checks (always run, on EVERY book, regardless of currency classification; each is a HALTING gate).** These validate the server's OWN numbers are self-consistent, independent of local math and of FX entirely:
    1. `|sum(company_contribution[].total_pl) − portfolio_summary.total_pl| / portfolio_parameters.initial_value ≤ 1 bp`.
    2. `|sum(sector_contribution[].total_pl) − portfolio_summary.total_pl| / portfolio_parameters.initial_value ≤ 1 bp`.
    3. `|portfolio_summary.total_pl / portfolio_parameters.initial_value − portfolio_summary.total_return| ≤ 1 bp`.
    Any failure halts rendering with "Server internal-consistency check failed: {which identity}, diff {N} bps" — this signals corrupted or inconsistent server data and is never explained by FX, local math, or currency classification.
  - **`effective_date` IS the ex-date.** Verified on two markets: VZ.N (US, 2026-07-10) and OCBC.SI (SGX) — on 2026-08-17, the server applied OCBC's 0.47 dividend using `effective_date` 2026-08-17, not the `record_date` 2026-08-18. Build `dividend_schedule` keyed on `effective_date` directly; do not substitute `record_date` or `pay_date`.
  - **A dividend endpoint failure is NOT the same as a clean empty result.** `get_stock_outlook(aspect="dividends")`'s underlying call catches its own exceptions and returns an empty list on error — a holding with genuinely zero dividends and a holding whose call errored both come back as `[]`. Treat an empty list as "zero dividends, verified" by default; only mark a holding dividend-unchecked when the call itself errors (raises / times out / returns something that is not a list) or when a record for that holding is dropped as malformed (see the next bullet) — an empty list on its own is NOT a reason to mark a holding unchecked. Because of this collapse, an empty list is weak evidence for a high-yield name specifically — note that in About This Report rather than treating a quiet `[]` as proof the name pays nothing.
  - **Malformed records are dropped per holding, not the whole call.** A record with a null or non-numeric `divrate` or a date outside the period: drop that one record and mark the holding dividend-unchecked, but keep processing that holding's other records and every other holding's records — the audit continues on whatever is left. A date that is not an actual close for that holding is NOT malformed (BUG-009) — pass it through; `contribution.py` shifts or marks it unapplied itself.
  - **Same ex-date, several events: sum them; dedupe exact duplicates.** OCBC.SI paid both a FIN (0.42) and an SPL (0.16) dividend on the same 2026-04-23 ex-date — `dividend_schedule[symbol][effective_date]` is the SUM of every distinct cash-dividend record on that date, not just the first one seen. Before summing, drop exact duplicate rows (same `effective_date`, `divtypecode`, and `divrate`) — a duplicate row is a re-fetch artifact, not a second event.
  - **Dividend-call / coverage failure.** If a holding's `get_stock_outlook(aspect="dividends")` call errors, a record for an ex-date inside the period is dropped as malformed or excluded (currency mismatch, unhandled `divtypecode`), or `contribution.py`'s result names that holding under `dividends_unapplied` (BUG-009: an ex-date with no later close in the period to shift to), that holding's dividend contribution cannot be fully verified: mark it dividend-unchecked and list it under coverage gaps (Step 5 §10). Still run the audit on whatever dividend data IS available for the other holdings — a resulting >25-bp failure may be partly explained by the missing dividend, but the tolerance is never widened to compensate; investigate and report the gap instead.
  - `portfolio_summary.total_fx_pl` is the classification signal itself (see "Classify the book first" above) — `== 0` (within rounding) means single-currency and the exact 25-bp gate applies; nonzero means multi-currency and the comparison is informational only. The comparison TARGET is always `total_price_pl` either way; what changes is whether a divergence against it halts.
  - This skill has no base-currency price source, so converting local prices to base currency is not an option — do not invent one.
- `prior_portfolio` and `trade_log` are HARD-REQUIRED. Reject incomplete invocations with the accepted-shape examples in Inputs. No silent degradation to position-only contribution.
- `daily_prices` MUST be price-return prices — raw daily closes, no dividend adjustment; this is what `export_price_series` actually returns. Local `contribution.py` combines these with the per-holding `dividend_schedule` built from Batch A's `get_stock_outlook(aspect="dividends")` calls (ex-date = `effective_date`, cash amount = `divrate`) to compute a total return before FX: dividends ARE captured, via the schedule; FX is not (see the reconciliation gotcha above for the residual accounting). Do not feed dividend-adjusted / total-return prices directly into `daily_prices` as a substitute for `dividend_schedule` — that smears the dividend's economic impact across many days instead of landing it on the ex-date, and if `dividend_schedule` is ALSO supplied for the same symbol, double-counts the dividend (see `test_total_return_style_prices_plus_dividend_schedule_double_counts_negative_control`). `contribution.py` reads this on a calendar-daily grid matching the server's: a symbol missing a price on a date some OTHER symbol has is forward-filled from its own last known close with a zero return that day, not rejected. Every symbol needs a price AT OR BEFORE `period_start` (BUG-004) — if `period_start` itself isn't a trading day, that anchor is forward-filled from the symbol's own last close before it, so callers must keep pre-`period_start` history rather than slicing it away (see Step 2's `export_price_series` row). A dividend's `ex_date` that is not an actual close for that symbol is no longer rejected (BUG-009): it is shifted to that symbol's next actual close in the period, or left unapplied — and recorded as such — if none exists (see `dividends_shifted` / `dividends_unapplied` in the Math Reference).
- `divrate` is as-declared on the ex-date; it is not split-adjusted. If a stock split occurs between a dividend's ex-date and the period end, scale that `divrate` by the split factor before putting it in `dividend_schedule`, or — if the split factor is not available — mark the holding dividend-unchecked rather than feeding in a stale per-share amount.
- **BUG-010: split handling for `export_price_series` closes themselves (not just `divrate`) is UNVERIFIED.** Whether `export_price_series` returns split-adjusted history is not established. If a stock split occurs for a holding during the period, do not assume the raw closes already account for it — a real split shows up as a price-return formula seeing a spurious multi-fold jump that is not an actual return. Mark that holding **audit-unchecked** (a new, distinct category from dividend-unchecked — list both separately under coverage gaps, Step 5 §10) rather than guessing a split factor or silently accepting the jump into the reconciliation audit.
- Per-mover fan-out cap: 5 contributors + 5 detractors = 10 names max. Do not exceed.
- Soft cap on holdings: 40. Auto-truncate to top 40 by current weight; surface "Holdings 41-N (X% weight) excluded from per-position analysis". Daily contribution math runs over the FULL set; only per-mover fan-out is truncated.
- `macro_analyst` parameter is `market` (not `country`). Cap macro coverage at 3 markets.
- Period start must be within the trailing 365-day window from today (\`export_price_series\` limit — trailing from today, no start/end anchor). For periods starting >365 days ago, reject with a v2-roadmap note.
- Output is Word .docx ONLY via the `docx` skill chain. Markdown is an intermediate artifact, never the deliverable.
- Materiality tiers for excluded holdings: ≤5% total → in-line "Coverage gap" note above contributors table; >5% → high-visibility WARNING banner at top; any single holding >10% → reject the attribution section entirely.
- Driver-field fallback hierarchy: (1) news event with date from `get_news_synthesis`, (2) factor score change from `get_score_analysis`, (3) sector movement from `analyze_portfolio` `sector_contribution` / `sector_allocation` (this skill never calls `get_peer_snapshot`, and `analyze_portfolio` returns no peer data), (4) default phrase ("Price appreciation in line with [sector / market]" or "Multiple expansion / contraction"). Never render an empty driver slot.
- Empty contributor / detractor side: if all holdings have positive (negative) `contrib_bps` per the Step 4 basis guard, render the populated table only; suppress the empty side rather than rendering "No detractors" prose.
- Single-holding portfolio: top-5 collapses to top-1 (or top-N for N < 5); render valid for N ∈ [1, 5].
- Duplicate symbol in input portfolio: reject at validation with "Duplicate symbol {sym}" — no auto-dedup.
- Mid-period delisting (price series ends before period_end): treat as a coverage gap (drop from rankings + surface per the materiality tiers), not a hard ValueError.
- This skill is private-beta gated; excluded from default `build-skills.sh` builds. Confirm enablement before running for new customers.
- JIT-load `_parallax/white-label/integration-pattern.md` in Step 0; that doc carries the loader call (`load_visual_branding`), error-state contract, docx substitution table (§6), and About This Report template (§7). Step 5 applies it; the substitution table lives in §6.
- Every host interaction is a host primitive from `parallax-conventions.md` §14 (bindings §14.2, fail-open §14.3). The `docx` skill chain is `invoke-skill`; `scripts/contribution.py` is `run-shell`.
- Voice and auto-jurisdiction disclaimers remain explicitly out of scope (see "Not in scope"). This skill uses `load_visual_branding()` rather than `load_client_branding()` — the 7-key wrapper excludes `branding["voice"]` at code level, so accidental access raises `KeyError`. The CIO writes the prose; the standard wording in the **Disclaimer** section stays. Visual branding only.

Generate a structured Word document that a fund-manager CIO can edit and send to LPs as the period letter. The pack covers the period dates, gross return / drawdown / vol, attribution snapshot, top 5 contributors and bottom 5 detractors with evidence-backed drivers, trade-log narrative, macro snapshot, news themes, a conditional forward-outlook (only if a house view is active), coverage gaps, and the standard disclaimer.

## Usage

```
/parallax-cio-letter-prep <inputs.json>
```

Where `inputs.json` provides the structured inputs in the shapes below. The CIO reviews, edits in Word, and sends to LPs. The skill never sends or stores anything externally.

## Inputs

| Field | Required? | Shape | Notes |
|---|---|---|---|
| `current_portfolio` | yes | `[{"symbol":"AAPL.O","weight":0.25}, ...]` | RIC format. Weights sum to ~1.0. **These are the DECLARED target weights after the last trade** (`prior_portfolio` walked forward through `trade_log`'s deltas) — NOT the drifted/compounded ending weights a buy-and-hold price path would produce (BUG-011). Same convention `contribution.py` and `analyze_portfolio`'s multi-date `portfolio` array use. |
| `prior_portfolio` | **yes** | `[{"symbol":"AAPL.O","weight":0.20}, ...]` | Period-start snapshot. Hard-required — anchor for trades. |
| `trade_log` | **yes** | `[{"symbol":"NVDA.O","action":"enter","date":"2026-04-15","weight_delta":0.05}, ...]` | Chronologically ordered. Actions ∈ {`add`, `trim`, `enter`, `exit`}. Same-date weight_deltas should sum to zero across symbols. Hard-required — without it, the math is silently wrong when positions change mid-period. A trade dated on a non-trading day (weekend, a market holiday) is never dropped (BUG-003): `contribution.py` applies it after the close of the latest priced date at or before its own date. |
| `period_start` | yes | ISO `YYYY-MM-DD` | Inclusive. |
| `period_end` | yes | ISO `YYYY-MM-DD` | Inclusive. Period length must be ≤ 365 days. |
| `benchmark` | optional | `"SPY.N"` or RIC | If supplied, attribution snapshot includes excess return. |
| `length_target` | optional | `"short"` (≤ 600 words) \| `"standard"` (≤ 1000) \| `"long"` (≤ 1500) | Default: `"standard"`. Affects narrative density, not table content. |
| `house_view` | optional | view manifest per `_parallax/house-view/loader.md` | Forward-outlook section ONLY. |

### Step 1 — Resolve inputs

1. Validate inputs: weights sum to 1.0 (within 1e-3), period ≤ 365 days, trade_log chronologically ordered, weight_delta sums per date balance to zero, no duplicate symbols. Missing `prior_portfolio` or `trade_log`: reject with the accepted-shape example.

### Step 2 — Fetch (parallel batches)

#### Batch A — Period analytics fan-out

`call-tool` all rows below together. Every row is independent.

| Tool | Parameters | Notes |
|---|---|---|
| `get_telemetry` | fields: regime_tag, signals, commentary.headline, commentary.mechanism, divergences | Market regime context for the period header. |
| `analyze_portfolio` | Construct the `portfolio` array as one entry at `period_start` carrying `prior_portfolio` weights, plus one entry per distinct trade date in `trade_log` carrying the cumulative-post-trade weights as of that date. **BUG-005: if any trade is dated exactly `period_start`, do NOT emit a separate entry for it** — merge it into the single `period_start` entry, which then carries the cumulative weights AFTER that trade (not the pre-trade `prior_portfolio` weights), matching `contribution.py`'s own convention that a `period_start`-dated trade applies before return-day 1 (see Math Reference). The array has exactly one entry per DISTINCT date, never two entries sharing the same date. The final entry's weights MUST equal `current_portfolio`. `start_date=period_start`, `end_date=period_end`, `benchmark=<input or "ACWI.OQ">`, `fields=["portfolio_summary","performance_metrics","drawdown_analysis","portfolio_scores","concentration_metrics","company_contribution","sector_contribution","sector_allocation","time_period_returns","latest_holdings","portfolio_parameters"]`. For the common single-rebalance case (one trade date `D` strictly after `period_start`), the array has 2 entries: `[{date: period_start, ...prior}, {date: D, ...current}]`. | **Single multi-date call.** Server-side `company_contribution` is canonical; current+prior factor exposures via `latest_holdings` + `sector_allocation` over time. `scripts/contribution.py` runs as the reconciliation audit (Step 3); its BUG-006 oracle test (`test_contribution_server_oracle.py`) builds its own `portfolio` array the same way, to the same no-duplicate-date rule. |
| `export_price_series` | `symbol=<each holding>`, `days=<min((today - period_start).days + 5, 365)>` | One call per holding (parallel). Returns raw, price-return closes (no dividend adjustment). Trailing window anchored to period_start (today must be within 365 days of period_start); slice fetched prices to **`(-inf, period_end]`** before passing to `contribution.py` — keep every pre-`period_start` date the trailing window returned, do NOT lower-bound the slice to `period_start`. **BUG-004:** when `period_start` falls on a weekend or a market holiday, no symbol will have a literal close on that exact date; `contribution.py` forward-fills the `period_start` anchor from each symbol's own last close on or before `period_start`, and that fallback close only exists if the caller kept it instead of slicing it away. Fires for the FULL holdings set (input to local audit) — Batch B fan-out is the truncated set, not this. |
| `get_stock_outlook` | `symbol=<each holding>`, `aspect="dividends"` — **one call per holding, all fanned out in parallel within this batch** | 1 credit per call (conventions §0.2 / token-costs.md). Returns a flat list of per-holding dividend records (an empty list on a clean no-dividend holding AND on a server-side error — see the Gotcha above); relevant fields are `divrate` (cash amount), `effective_date` (ex-date — maps to `dividend_schedule`'s date key), `record_date`, `pay_date`, `currency`, `divtypecode`. First drop malformed records (null/non-numeric `divrate`, a date outside the period) and exact duplicate rows (same `effective_date`, `divtypecode`, `divrate`). Then, among the survivors, treat a record as a plain cash distribution — include it — only when `divtypecode` is one of the recurring codes (`QTR`, `MTH`, `HYR`, `YR`, `FIN`, `INT`, `INI`) or the special-cash code `SPL`; any other code is unhandled and excluded. Fires for the FULL holdings set (input to local audit), matching `export_price_series`'s scope — not the Batch B truncated set. |
| `get_company_info` | `symbol=<each holding>` — **one call per holding, all fanned out in parallel within this batch** | Ground-truth name oracle for the Step 3 identity gate. 1 credit per call, instant. Per-holding only — do NOT consolidate into a comma-joined call: comma-joined calls fail-empty on partial coverage, so a single unresolved RIC silently zeroes the whole batch, leaving the identity gate with nothing to compare and passing every holding. Per-holding calls also mean the single-symbol `GET_COMPANY_INFO_SCHEMA` and its mock model the response this skill actually receives. |
| `check_portfolio_redundancy` | `holdings=current_portfolio` | Surfaced under coverage gaps if low coverage; otherwise informs trade-narrative quality. |

Asset-class scope: this skill assumes equity legs only (single-stock fund-manager portfolios). `export_price_series` is the correct call for every holding. If a holding resolves to ETF, branch via `etf_daily_price` per the equity-branch convention; equity is the default Pre-classification gate.

If `export_price_series` fails for a holding, mark that holding as price-unavailable and apply materiality-tier handling in Step 3.

If `get_stock_outlook(aspect="dividends")` errors for a holding, a record for an ex-date inside the period is dropped as malformed or excluded (currency mismatch, unhandled `divtypecode`), or `contribution.py` reports the holding under `dividends_unapplied` (BUG-009), mark that holding as dividend-unchecked (per the reconciliation gotcha above) and list it under coverage gaps. A clean empty list is NOT dividend-unchecked — it means zero dividends, verified (the endpoint collapses a genuine zero and a server-side error to the same `[]`, which is why only the error/malformed-record/unapplied paths above mark a holding unchecked). The audit still runs on whatever dividend data IS available for the other holdings; the 25-bp reconciliation tolerance is never widened to compensate for a missing dividend.

### Step 3 — Verify

**Identity gate.** Cross-validate each holding's identity per the `analyze_portfolio` row of the conventions §2 identity table: compare the per-row `name` in `latest_holdings[]` and `company_contribution[]` against `get_company_info.name` for the same `ric`, normalizing both sides first per §2 step 2 — `Apple Inc` and `Apple Inc.` are the same company and must not flag. Flag any mismatch that survives normalization and exclude mismatched holdings from aggregate factor calculations. A holding with a row in neither `latest_holdings[]` nor `company_contribution[]`, or whose `get_company_info` call fails or returns empty, has no name pair to compare and therefore cannot be identity-checked — record it as UNCHECKED and list it under coverage gaps rather than treating a missing comparison as a pass.

**Classify, then compare against the server's total-return-before-FX reference, `total_price_pl`.** `total_price_pl` is a TOTAL-RETURN field: dividends are included (added back on the ex-date), only FX is excluded (`total_fx_pl` plus a price×FX cross term) — ON A SINGLE-CURRENCY BOOK (see the reconciliation Gotcha above for the live verification, the owner-decided single-/multi-currency split, and why a multi-currency book's `total_price_pl` carries an additional FX-weight-drift cross term local math cannot replicate). Local `contribution.py` takes raw, price-return closes from `export_price_series` (no currency conversion) plus the `dividend_schedule` built from Batch A's `get_stock_outlook` calls, so it also includes dividends and excludes FX. The server's `total_return` and `total_pl` are base-currency numbers that additionally include `total_fx_pl`, so comparing local math against either of those fields directly would let a real local price-math bug hide behind offsetting FX content. Always compare against `total_price_pl`, never `total_return`/`total_pl` — but what a divergence against it MEANS depends on the classification:

1. **Classify:** `is_single_currency = (portfolio_summary.total_fx_pl == 0)` (within the same rounding budget as the reconciliation check); if `total_fx_pl` is absent, fall back to comparing every holding's listing currency (`get_company_info.currency` / `.data.currency`) against `portfolio_parameters.base_currency`. If classification itself cannot be resolved (either field absent, or a holding's currency unresolved), treat as `UNVERIFIED` per conventions §4.0 — do not guess, do not PASS.
2. `server_total_return_before_fx = portfolio_summary.total_price_pl / portfolio_parameters.initial_value` (resolve `initial_value` per the fallback chain in the gotcha above; if it cannot be resolved, halt with "cannot compute server total-return-before-FX (initial_value unresolved)" — never fall back to comparing against `total_return`).
3. **Single-currency, `|local − server_total_return_before_fx| ≤ 25 bps`** → **PASS, total return before FX.** Render server-side numbers in the pack; note "local audit passed, total-return-before-FX basis (diff {N} bps); FX not modeled by local audit" in About This Report, together with the FX-only residual in bps, `(total_pl − total_price_pl) / initial_value × 10000` (expect this near 0, since single-currency implies no FX exposure).
4. **Single-currency, `|local − server_total_return_before_fx| > 25 bps`** → **halt** rendering with "Reconciliation audit failed: local {X} bps vs server total-return-before-FX {Y} bps (diff {Z} bps exceeds 25-bp tolerance). Investigate before sending to LPs." — the gap isn't explained by FX (there is none) and is a real bug.
5. **Multi-currency (or classification `UNVERIFIED`)** → regardless of the diff's size, this comparison never halts. Render server-side numbers in the pack as usual (they remain canonical — see the Gotcha), and note in About This Report: `Reconciliation audit: INFORMATIONAL (multi-currency) — local total-return-before-FX {X} bps vs server {Y} bps; diff {Z} bps; not evaluated against the 25-bp gate (local math has no FX-weight-drift term)`.
6. If any holding was marked dividend-unchecked or audit-unchecked (Batch A / Step 2), note it in the halt-or-pass-or-informational message rather than widening the tolerance to compensate.

**Server internal-consistency checks (always run on EVERY book, halting on failure, regardless of currency classification)** — these audit the server's OWN numbers against each other, not against local math, so they are not affected by the FX gap above:

- `|sum(company_contribution[].total_pl) − portfolio_summary.total_pl| / initial_value ≤ 1 bp` → else halt: "Server internal-consistency check failed: company_contribution sum vs total_pl, diff {N} bps."
- `|sum(sector_contribution[].total_pl) − portfolio_summary.total_pl| / initial_value ≤ 1 bp` → else halt: "Server internal-consistency check failed: sector_contribution sum vs total_pl, diff {N} bps."
- `|total_pl / initial_value − total_return| ≤ 1 bp` → else halt: "Server internal-consistency check failed: total_pl/initial_value vs total_return, diff {N} bps."

The script's own 1-bp inner gate (`ReconciliationError` on `|sum(contributions) − portfolio_total_return| > 1bp`) still fires as the inner safety net, on every book — it is a property of `contribution.py`'s own walk, not of the server comparison, so currency classification does not affect it.

**BUG-011 — building the local-audit sub-book when Tier 1 or 2 fires.** `contribution.py` requires EVERY symbol named in `prior_portfolio`, `current_portfolio`, or `trade_log` to carry a price (it raises otherwise — it cannot silently skip a holding the way "Daily contribution math runs over the FULL set" might suggest). When one or more holdings are excluded for missing price data, build the sub-book passed to `contribution.py` as follows, not by retrying with the full inputs:

1. Reconstruct the FULL snapshot sequence first, exactly as Step 2 builds the `analyze_portfolio` `portfolio` array: `prior_portfolio` at `period_start`, then one cumulative-weights snapshot per distinct trade date, ending at `current_portfolio`. (This is a sequence of complete weight dicts, not a diff — build it by walking `trade_log`'s deltas forward from `prior_portfolio`, the same walk `contribution.py` does internally.)
2. In EVERY snapshot in that sequence, drop each excluded symbol's entry, then **renormalize that snapshot alone** so its remaining weights sum back to 1.0 (divide each remaining weight by `1 - excluded_weight_at_that_snapshot`; the excluded weight can itself change snapshot to snapshot if a trade touched the excluded symbol before it was known to be excluded — use whatever weight it actually carried at each snapshot).
3. **Re-derive `trade_log` deltas from the renormalized snapshots** — for each pair of consecutive renormalized snapshots and each surviving symbol, `weight_delta = weight_at_later_snapshot − weight_at_earlier_snapshot`. Do NOT scale the ORIGINAL deltas: scaling them does not reconstruct the renormalized ending weights (the excluded symbol's dropped delta leaves a survivor's original delta unbalanced), and `contribution.py`'s own `current_portfolio` cross-check will raise on that inconsistency. Re-deriving from the renormalized snapshots directly guarantees each date's deltas sum to zero across survivors by construction, since both snapshots in a pair already sum to 1.0.
4. Run `contribution.py` on this renormalized sub-book (renormalized `prior_portfolio`, renormalized `current_portfolio`, re-derived `trade_log`). Its `portfolio_total_return` is a **SUB-BOOK total**, inflated relative to the true book because the excluded holding's weight was redistributed to the survivors rather than removed from the total — it is NOT directly comparable to `total_price_pl / initial_value`, which the server derives from the FULL book.
5. **Any Tier 1 or 2 exclusion downgrades the local-vs-server comparison to INFORMATIONAL**, exactly like the multi-currency case above, with its own one-line explanation: `Reconciliation audit: INFORMATIONAL (N holding(s) excluded, sub-book renormalized) — sub-book total {X} bps is not on the same basis as the full-book server total and is not evidence of a bug`. Never report a sub-book match as PASS. The server internal-consistency checks (always-run, above) are unaffected — they compare the server's own numbers to each other and do not depend on the local sub-book at all.

`current_portfolio` is always the DECLARED target weight after the last trade (`prior_portfolio` walked forward through `trade_log`) — the same convention `contribution.py`'s own docstring uses and the same convention `analyze_portfolio`'s multi-date `portfolio` array uses. It is NOT the drifted/compounded ending weight a buy-and-hold walk would produce; do not derive it by compounding `prior_portfolio` through the price path.

## Failure modes

- `prior_portfolio` or `trade_log` missing, duplicate symbol, period > 365 days, or period start > 365 days ago: reject before any Parallax call.
- Reconciliation audit: compares local `portfolio_total_return` (price + dividends via `dividend_schedule`, no FX) against the server's total-return-before-FX figure (`total_price_pl / initial_value`) — see the reconciliation gotcha. **Single-currency book:** `|local − server_total_return_before_fx| > 25 bps` halts rendering with the diff; within 25 bps reports PASS on a total-return-before-FX basis, not a halt. **Multi-currency book, or an unresolved currency classification, or a Tier 1/2 price-exclusion sub-book:** this comparison is informational only and never halts, regardless of the diff's size — the FX-weight-drift cross term (multi-currency) or the renormalized sub-book basis (BUG-011) makes it not comparable at the 25-bp gate. The three server internal-consistency checks (company/sector `total_pl` sums; `total_pl/initial_value` vs `total_return`) always run and always halt on failure, on every book regardless of currency. The script's own 1-bp `ReconciliationError` always halts. Never catch-and-discard.
- `contribution_pct` basis guard matches neither `total_return` nor `1.0`: halt rendering with the diff; the basis is unknown and the numbers cannot be trusted.
- `export_price_series` fails for a holding: price-unavailable → materiality tiers (Step 3); any single holding > 10% rejects the attribution section.
- `get_stock_outlook(aspect="dividends")` errors for a holding, or a record is dropped as malformed, or excluded for a currency mismatch / unhandled `divtypecode`, or `contribution.py` reports it under `dividends_unapplied` (BUG-009): the holding is dividend-unchecked and listed under coverage gaps. A clean empty list (genuinely zero dividends) is NOT dividend-unchecked. The reconciliation audit still runs on the remaining holdings' dividend data, and the 25-bp tolerance is never widened to compensate.
- A stock split occurs for a holding during the period (BUG-010): mark that holding audit-unchecked and list it under coverage gaps — split-adjustment for `export_price_series` closes is unverified; never guess a split factor.
- `get_company_info` fails or returns empty: the holding is UNCHECKED and listed under coverage gaps; never a pass.
- Async tools pending at render: `[news pending]` placeholder per conventions §5; complete on resolution.
- `invoke-skill` (docx) unavailable: stop with the structured content on disk and say the `.docx` could not be produced on this host; do not hand over Markdown as the deliverable.

- About This Report carries the reconciliation line, the branding line, and the private-beta tag; §9.2 disclosure sits immediately above the disclaimer.
- Coverage gaps list every excluded, truncated, UNCHECKED, dividend-unchecked, or audit-unchecked holding.

## Math Reference: scripts/contribution.py

Function: `daily_contribution(prior_portfolio, current_portfolio, trade_log, daily_prices, period_start, period_end, dividend_schedule=None, reconciliation_tolerance=1e-4)`.

- **Required-input contract:** the first six positional arguments (`prior_portfolio` through `period_end`) are required. The function rejects empty / mismatched / out-of-order / out-of-period inputs with a `ValueError`, including a cross-check that `prior_portfolio + trade_log` reconstructs `current_portfolio` within 10 bps of weight per symbol.
- **Replicates the server's compounding/rebalancing method:** between rebalances, each holding's value compounds daily (`value[d] = value[d-1] * (1 + r[d])`) — weights drift with relative performance. On a rebalance date, that day's return applies to the pre-rebalance value first; only then does the book reweight to the new target (trade after close). Per-holding `contribution` is that holding's dollar P&L; `portfolio_total_return` is `final_total_value / initial_total_value − 1`, derived independently of the per-holding sum (see the reconciliation gate below).
- **Calendar forward-fill:** every symbol needs a price exactly on `period_start`; a later date on which a given symbol has no price of its own is forward-filled from its last known close with a zero return that day, matching the server's calendar-daily grid.
- **Price-return-prices contract:** `daily_prices` MUST be price-return prices — raw daily closes, no dividend adjustment; this is what `export_price_series` actually returns, so pass its outputs directly. Passing dividend-adjusted / total-return prices directly instead of using `dividend_schedule` is wrong under this contract — see `test_total_return_style_prices_plus_dividend_schedule_double_counts_negative_control` for the negative control.
- **`dividend_schedule` (optional, default `None` → empty) — total return before FX, not price-only:** `{symbol: {ex_date: cash_amount}}`, cash amount in the holding's own listing currency, `ex_date` = `get_stock_outlook(aspect="dividends")`'s `effective_date`. If `ex_date` is not an actual close for that symbol, it is SHIFTED to that symbol's next actual close in the period, or UNAPPLIED if none exists (BUG-009 — reported in the result, not raised; see `dividends_shifted` / `dividends_unapplied`). With it applied, that ex-date's return becomes `(price + cash_amount) / prior_price − 1` instead of the plain price-return formula, and the reported `portfolio_total_return` becomes a total return before FX — the SAME basis as the server's `total_price_pl` **on a single-currency book** (see the Step 3 reconciliation gotcha: live verification established `total_price_pl` includes dividends and excludes only FX on a single-currency book; a multi-currency book's `total_price_pl` additionally carries an FX-weight-drift cross term, so the comparison there is informational, not exact — see the owner decision in Step 3). Cash amounts must be finite and non-negative. Omitting it (the default) preserves the original price-only behavior — useful for `test_price_return_prices_with_ex_dividend_drop_compute_correctly`-style sanity checks, but NOT what the pack should pass when reconciling against `total_price_pl`.
- **Reconciliation gate:** the function computes `diff = sum(contributions) − portfolio_total_return` — two independent accumulations of the same walk (one the running per-day P&L sum, the other derived from the literal end state of the per-holding value dict) — and raises `ReconciliationError(diff, tolerance)` if `|diff| > 1e-4` (1 bp) or if `diff` is not finite. The skill MUST NOT catch and discard this error — surface it with the diff value and abort rendering. The gate is a real identity check, not a tautology: it is exact for a book with no rebalance, and it fires whenever a rebalance's target weights do not sum to 1.0 at the moment they are applied, even transiently (see `test_reconciliation_gate_fires_on_a_transient_weight_imbalance_that_nets_to_zero`).
- **Returns:** `{contributions: {symbol: decimal_contribution}, portfolio_total_return: final_total_value_over_initial_minus_one, reconciliation_diff: signed_diff}`. `contribution_bps = decimal_contribution * 10000`.
- **No arithmetic-vs-geometric gap, no rebalance-date skew — on a single-currency book.** This module compounds, exactly as the server does, and reweights after a rebalance date's close, exactly as the server does — see `test_vz_single_holding_with_dividend_schedule_matches_server_total_return`, which now matches the server's reported `total_price_pl`-implied return to within 1e-5 rather than a 25-bp allowance, and `test_contribution_server_oracle.py` (BUG-006), which cross-checks a multi-holding, multi-rebalance, dividend-bearing book against an independently ported server-walk implementation to within 1e-9. The residual 25-bp SKILL.md tolerance (Step 3) covers data differences only on a single-currency book — vendor dividend data vs the dividend-event feed, and the calendar-fill convention — not a method gap. **On a multi-currency book there IS a known, un-closed gap:** the server's `total_price_pl` carries an FX-weight-drift cross term (base-currency weights drift with FX, not just with price) this module cannot replicate, which is why Step 3 treats that comparison as informational rather than exact.
- **Trade-date snapping (BUG-003) and the period_start anchor (BUG-004).** A trade dated on a non-trading day is applied after the close of the latest priced timeline date at or before its own date, never dropped. A symbol missing a literal close on `period_start` itself has its anchor forward-filled from its own last close at or before `period_start`, never raising unless no such close exists at all. Both are exercised together in `test_contribution_server_oracle.py` and individually in `test_contribution_edges.py`.
- **Split handling is unverified (BUG-010).** `contribution.py` has no way to tell whether `export_price_series` closes are split-adjusted; a split during the period makes the price-return formula see a spurious jump. SKILL.md marks the affected holding audit-unchecked rather than guessing a split factor — `contribution.py` itself does not attempt split detection.

## Design Lineage

The skill's design choices, summarized inline so the rationale is self-contained:

| Choice | Rationale |
|---|---|
| Daily contribution analysis (not naive `weight × period_return`) | Naive math is silently wrong when positions change mid-period. Daily reconstruction from prior + trade_log is the only correct approach for rebalanced portfolios. |
| Hard-require `prior_portfolio` + `trade_log` | Without both, the math falls back to wrong-by-default. Better to reject than silently degrade. |
| House view scoped to forward-outlook section ONLY | Letter is retrospective; view is forward-looking. Mixing them creates anachronism risk in the LP narrative. |
| Tight composition templates with required evidence slots | Free-form prose drifts into generic platitudes. Templates force evidence-anchored drivers. |
| Materiality tiers for excluded holdings | Drop-with-note is insufficient when the dropped holding is a top contributor. Tiers ensure user-visible warnings scale with materiality. |
| Word .docx output via the `docx` skill chain | Fund managers write LP letters in Word. Native format reduces friction and matches CIO workflow. |
| White-label visual substitution (palette + fonts + logo); voice and disclaimers stay v2 | Visual branding is independent of prose; replacing the default Parallax-CG palette with the fund's own brand makes the .docx look like the fund's collateral without touching the killed-premise voice-generation territory. Voice and auto-disclaimers remain explicitly out of scope (see "Not in scope") because the CIO writes the prose and reviews the disclaimer; pulling either from a config silently would violate the design's compliance posture. |
| Server-side `company_contribution` as canonical numbers | Parallax's server-side math is what CIO will defend in LP meetings. Local `contribution.py` is the audit gate, not a substitute for the LP-facing cells. The endpoint's `contribution_pct` basis has changed server-side before (P&L share summing to 1.0, pre-2026-10; return contribution summing to `total_return` since) with no client-visible version signal on this skill's ad-hoc `analyze_portfolio` calls, so Step 4 runs a cheap basis guard and converts only when the retired basis is detected, rather than assuming either basis. |
| 5+5 contributor/detractor cap with 40-holding soft cap | Async per-mover MCP calls are expensive (~30-90s each). Caps balance cost against narrative depth. |
| Driver fallback hierarchy (news → factor → sector → default phrase) | Real news is best evidence; default phrases prevent broken row rendering when no signal exists. |
| Reconciliation gate + 25-bp audit tolerance | Inner 1-bp gate catches math bugs in `contribution.py` — a real identity check between two independent accumulations of the same walk, not a tautology (see Math Reference). Outer 25-bp gate catches local-vs-server divergence; since `contribution.py` replicates the server's compounding/rebalancing method exactly, the residual covers data differences (vendor dividend data vs the dividend-event feed, calendar-fill convention) rather than a known method gap. |
| Reconciliation compares against the server's total-return-before-FX field, `total_price_pl`, never `total_return`/`total_pl` directly — exact gate on a single-currency book, informational on a multi-currency book | Live verification (single-holding VZ.N book, 2026-10-06) established `total_price_pl` includes dividends (added back on the ex-date, compounded forward) and excludes only FX — the earlier design assumed it was price-only, which was wrong. `contribution.py` now takes raw, price-return closes from `export_price_series` PLUS a `dividend_schedule` built from `get_stock_outlook(aspect="dividends")`, giving it the same basis: dividends included, FX excluded. On a SINGLE-CURRENCY book that basis matches `total_price_pl` exactly (to data noise, within 25 bps), so a divergence there is a real bug. On a MULTI-CURRENCY book, `total_price_pl` carries an additional FX-weight-drift cross term (`price_pl = starting_value_base × changepercent`, and the server's base-currency weights drift with FX as well as with price) that `contribution.py` has no way to replicate — it has no currency-conversion step at all. Owner decision (2026-10-07): rather than force every multi-currency book to a FAIL it cannot clear, or silently widen the tolerance until it masks a real bug, that comparison is reported as informational and never halts; the three server-internal-consistency checks (company/sector `total_pl` sums; `total_pl/initial_value` vs `total_return`) still run and still halt on every book, giving a multi-currency book real audit coverage that does not depend on the FX gap this skill cannot close. |
| Private-beta gate | Pilot with named customer first; promote after one full letter cycle of feedback. |
| MCP contract tests | Catch upstream Parallax schema drift in CI before customers hit it. |
