# Decision Log

This file captures the *why* behind each shipping milestone — alternatives that were rejected, flip conditions that would reverse the decision, verification status. For the *what* (one-line summary of what landed), see [CHANGELOG.md](CHANGELOG.md).

Conventions: each entry leads with **Why**, **Impact**, and **Alternatives**. `[DROP]` tags rejected alternatives. **Flip conditions** name the future state in which the decision should be revisited. Long entries are intentional — readers should be able to reconstruct the call without external context.

## 2026-08-20: Relabel `parallax-halal-screen`'s thresholds from "AAOIFI/DJIM" to commonly used screening ratios — no threshold value changes

**Why.** The skill's three Shariah screening thresholds carried the label "AAOIFI/DJIM" in six places, including the client-facing disclaimer emitted on every run. Verified against the published methodology documents (sources below), that label matches neither named standard: AAOIFI Standard 21 sets the debt cutoff at 30% of 12-month average market capitalization; Dow Jones/S&P Shariah sets it at 33% of trailing 24-month average market capitalization; the skill uses 33% of **total assets**, a denominator neither AAOIFI nor DJIM uses. The 5% non-permissible-income threshold IS common to AAOIFI, S&P/DJ, and MSCI, so that element of the label was defensible; the debt-ratio attribution was not. Every screen run therefore shipped a false standards-conformance claim on its disclaimer.

**Impact.**
- The six "AAOIFI/DJIM" mentions in `skills/parallax-halal-screen/SKILL.md` are relabeled to describe the thresholds as commonly used screening ratios, with the denominator (total assets) stated explicitly rather than implied by a standard name. "Conventional" was avoided as the label because in Islamic finance it is the standard antonym of Shariah-compliant, and this same file uses it in that sense for a prohibited industry.
- **No threshold value changed.** The 33% debt cutoff, the total-assets denominator, and the 5% non-permissible-income threshold are all unchanged.
- The regenerated `plugin/skills/parallax-halal-screen/SKILL.md` lands in the same change; `plugin/` is machine-built by `build_bundle.py plugin` and is never hand-edited.

**Alternatives.** [DROP] Relabel to "MSCI/FTSE" — rejected; the skill's 33% is not identical to MSCI/FTSE's 33.33%, so claiming that standard verbatim would be the same category of error being fixed. The deeper reason is the ratio SET, not the value: the MSCI Islamic Index Series applies three total-assets ratios at 33.33% (total debt; cash + interest-bearing securities; accounts receivable + cash), and this skill screens only the first two. Omitting the receivables ratio makes this screen materially more permissive than MSCI's, so no MSCI-derived label is defensible at any cutoff value while that ratio is absent. [DROP] Change the debt cutoff to 33.33% to match MSCI/FTSE exactly, or to 30% to match AAOIFI, while relabeling — rejected; a threshold VALUE change flips verdicts for holdings near the boundary, which is a behavior change requiring its own PR, its own regression fixtures, and its own decision entry. This entry covers the label only.

**Flip conditions:** (a) a decision to match a named index methodology in FULL — its cutoff value AND its complete ratio set, which for MSCI means adding the accounts-receivable + cash ratio this skill does not screen (a value-and-coverage change PR, per the [DROP] above) — only then would a provider-derived label be defensible; matching 33.33% alone is not sufficient and must not be read as satisfying this condition; (b) a Shariah board approves a specific named methodology for this skill — the label should then name that methodology and the thresholds should be brought into conformance with it in a value-change PR.

**Sources:**
- AAOIFI Standard 21: https://oicexchanges.org/files/1---shari-ah-screening-in-the-islamic-capital-markets-dr-hamed-merah-secretary-general-aaoifi.pdf
- S&P Dow Jones Islamic Market Indices Methodology: https://www.spglobal.com/spdji/en/documents/methodologies/methodology-dj-islamic-market-indices.pdf
- MSCI Islamic Index Series Methodology (2024-10-30): https://www.msci.com/indexes/documents/methodology/2_MSCI_Islamic_Index_Series_Methodology_20241030.pdf
- FTSE Russell Shariah methodology: https://research.ftserussell.com/products/index-notices/home/getmethodology/?id=266328

**Note:** the pre-existing "AAOIFI/DJIM" mentions elsewhere in this file (2026-05-25, halal-screen concentration sanity-check, N≥8) document an unrelated sector-exclusion heuristic decision and are not contradicted by this fix; left untouched.

## 2026-08-19: Make both cap tolerances relative, and derive the post-condition's value structurally rather than from a sweep

**Why.** `_apply_exposure_cap` tested `w > EXPOSURE_CAP * neutral[s] + 1e-12`. An absolute slack against a quantity that scales with `neutral[s]` admits a ratio of `EXPOSURE_CAP + 1e-12 / neutral[s]`, unbounded as the weight shrinks — 3.000000x at `neutral = 1e-13`, inside the documented contract. This is the fifth round on this function. The first three fixed the algorithm; this one fixes a constant whose FORM was wrong.

**Impact.**
- **Detection is relative:** `EXPOSURE_CAP * neutral[s] * (1 + CAP_REL_TOL)`, bounding the worst undetected ratio at `EXPOSURE_CAP * (1 + 1e-12)` at every scale.
- **A post-condition guards the output**, raising `AttributionError`, placed inside `_apply_exposure_cap` so both call sites are covered.
- **Negative / non-finite / missing neutral raises; `0.0` stays in contract.** The zero case is provably benign and HEAD honoured it, so rejecting it would have narrowed a documented contract for no gain.
- **The three validation checks are NOT duplicated in the post-condition.** They were, briefly. Removing them matters beyond tidiness: with the checks in both places, deleting the precondition entirely still raised on three of the four bad inputs, so the precondition was only partly pinned. One owner, one test.

**Alternatives.**
- `[DROP]` **`math.isclose(rel_tol=...)`.** Same threshold via a two-sided predicate scaling by the wrong operand; less legible, marginally less conservative at denormals.
- `[DROP]` **Flooring neutral weights.** Silently redefines the pinned counterfactual, needs an arbitrary threshold, sits adjacent to the downside floor `loader.md` forbids.
- `[DROP]` **Do nothing and document.** The `weights_for_groups` docstring promised the guarantee "for any `neutral_w` summing to 1". The counterexample satisfies that precondition exactly and returns 3.0x, so either the code or the promise had to change; the code was four lines.
- `[DROP]` **Calibrating `CAP_POST_TOL` to a percentile of a random sweep.** This was the first proposal and it is wrong. The p50 breach of the oscillation defect reconstructs across four decades depending on the generator, straddling the candidate value — so "1e-9 misses the median" flips sign with the seed. That is the seed-dependent-constant error the 2026-08-18 entry exists to reject, reintroduced one level up.
- `[DROP]` **A strict `1e-14` property check over a seeded sweep.** Unsound: the detection tolerance is part of the OUTPUT contract, so a free name may legitimately sit at `EXPOSURE_CAP * neutral * (1 + 1e-12)`. A measured "floor" of `4.4e-16` was a window-probability artifact — random sweeps never enter a window of relative width `1e-12`. A 1e-14 check would fire on correct code; a fixture at an ordinary neutral of 0.1 overshoots by `2.000622e-13` legitimately.

**The sound derivation, replacing the sweep.** Any relative post-condition threshold strictly greater than `CAP_REL_TOL` provably cannot fire on correct code, by the loop's exit invariant: capped names sit at exactly `EXPOSURE_CAP * neutral`, and free names satisfy `w <= EXPOSURE_CAP * neutral * (1 + CAP_REL_TOL)`. `1e-9` gives three decades of margin. No sweep, no percentile, no reachability estimate.

**What the post-condition does NOT do.** It is not the guard that pins the tolerance form; the two boundary fixtures are. An earlier draft claimed the post-condition could never catch a reverted tolerance at any threshold. That was false, falsified two ways: the plan's own mutation text contradicted it, and a directed fixture at an ordinary neutral of `0.1` produces a `2.000178e-12` overshoot that any tolerance above `CAP_REL_TOL` catches. The correct statement is narrower — **random sweeps do not exercise that window; a directed fixture must.**

**Flip conditions.** (a) `loader.md` specifies the cap tolerance explicitly → `CAP_REL_TOL` moves to match it. (b) A caller legitimately needs zero-neutral holdings excluded rather than admitted → the precondition changes and the docstring's "non-negative" qualifier with it. (c) A future edit captures a tolerance as a default argument rather than a module global → the guard-placement test fails on correct code, and the interface, not the test, is what changed.

**Verification.** 37 → 45 tests. Every figure cited here is pinned in a fixture, not quoted from a sweep — the fourth unreproducible number this repo has shipped was in the analysis this entry supersedes, so figures now live in tests that re-derive them on every run. Mutations proven to kill: detection reverted to absolute (2 tests), post-condition made absolute (1), post-condition moved to `weights_for_groups` (1), precondition deleted (1), precondition made to reject `0.0` (1), `CAP_REL_TOL = 0.0` (1), the two constants swapped (3), and the pair `M1 + post-condition removed` (3) — which proves the boundary fixtures are real tests and not post-condition shadows. One mutation, moving the post-condition call, is INVISIBLE alone on correct code and needed pairing to observe: with relative detection the routine never emits a breach, so placement cannot be seen until detection is also broken.

## 2026-08-18: Enforce the exposure cap on the model leg after coverage renormalization, and never on the realized leg

**Why.** The previous round made `weights_for_groups` honour the 2× cap on the dict it returns. That is not the quantity the report is built from. `active_return_bps` drops symbols with no return data and renormalizes both legs over the covered set, which multiplies every surviving ratio by `nw_total / w_total`. Dropping an overweighted name pushes that factor above 1 and carries a survivor past the cap. Roughly 38–40% of random 10–25 holding portfolios breached at realistic 5–20% drop rates, worst observed 3.09×. So the cap held on an intermediate value and failed on the reported one — a `loader.md` contract that reads "cap final exposure at 2× neutral" was true of a dict nobody consumes and false of `model_active_bps`.

This was raised as an out-of-scope known limit in the 2026-08-18 entry, flagged for an owner ruling on whether the renormalized ratio counts as "final exposure". The ruling is yes: the cap is a risk control, and a risk control that binds only before the data-coverage step is not one.

**Impact.**
- **The capping loop is extracted to `_apply_exposure_cap(weights, neutral_w)`**, called by `weights_for_groups` and again inside `active_return_bps` when `enforce_cap=True`. One implementation, two call sites — the alternative was a second copy that drifts, which is the failure mode this repo keeps closing.
- **`enforce_cap` is True at both MODEL sites** — `shapley_tilt_attribution`'s value function and the `model_active_bps` call in `attribute_segment`. Both must pass it or the per-tilt contributions stop summing to the total they are reported against.
- **`enforce_cap` defaults to False, and the realized leg keeps that default.** `tilted_actual` is reconstructed from the chain. It is what the book held, not what a model implies, and clamping it would overwrite a measured fact and silently shift `selection_residual_bps = actual − model`. A book genuinely 3× neutral in one name must report 3×. This is the single most important line in the change and the one a future "simplification" is most likely to get wrong. It is pinned by `test_attribute_segment_never_caps_the_realized_leg`, which drives `attribute_segment` and therefore reaches the actual call site. `test_the_realized_leg_is_never_capped` pins only the FUNCTION default: it calls `active_return_bps` directly and never reaches that line. This entry originally credited that test alone, which was false — adding `enforce_cap=True` at the call site passed all 36 tests until the wiring test was added. Pinning a helper and claiming the wired path is pinned is the recurring defect in this module; naming the wrong test in the record is the same error one level up.
- **`model_active_bps` and `selection_residual_bps` change value** for any segment with dropped holdings and a breaching tilt pattern. This is a deliberate behavioural change to a reported number, not a refactor.
- **The attribution suite now runs in GitHub CI.** It was in no root of `.github/workflows/evals.yml`, so the previous fix shipped with CI never running its regression tests.

**Alternatives.**
- `[DROP]` **Cap inside `active_return_bps` unconditionally.** Rejected, and it is the obvious wrong fix. That function is called on three weight sets, one of which is `tilted_actual`. Capping there corrupts the realized leg and the residual.
- `[DROP]` **Skip renormalization and compare legs on the original neutral.** Rejected — the legs then no longer sum to 1 over the covered set and the active return is not a portfolio difference at all.
- `[DROP]` **Leave the math and emit a coverage warning when dropped mass is material.** Rejected — a warning nobody reads is the same silent-pass failure in a new location, the reasoning already recorded in the 2026-08-15 render-gate entry.
- `[DROP]` **Restrict `weights_for_groups` to the covered set at construction.** Rejected — it has no access to `returns`, and threading coverage into it couples portfolio construction to data availability.

**Flip conditions.** (a) `loader.md` defines "final exposure" explicitly as the pre-coverage quantity → the model-leg enforcement becomes wrong and this reverts. (b) A consumer needs the uncapped model figure for diagnostics → it becomes an additional reported field, never a change to the capped default. (c) `active_return_bps` gains a fourth caller → classify it as model or realized before wiring, because the default is deliberately the realized one.

**Verification.** The capping extraction was verified behaviour-neutral first: 32 pre-existing tests green with no other change. The reproduction case goes 2.2500× → 2.0000× with the sum preserved to 1.1e-16. A 20,000-portfolio sweep at a 20% drop rate gives 0 breaches, worst ratio exactly `2.000000000`. Shapley efficiency survives the changed value function — worst `|Σ per_tilt − model_bps|` of `2.3e-13` bps over 3,000 portfolios. The realized leg was confirmed still reaching 2.98× (uncapped) in the same sweep. Five mutations, all caught. One of the four new tests was initially vacuous and one mutation initially SURVIVED — removing `enforce_cap=True` from the `model_bps` call site left all 35 tests green, because the test called `active_return_bps` directly instead of driving `attribute_segment`. `test_attribute_segment_wires_the_cap_into_model_active_bps` closes that by exercising the public entry point, and its own premise assertion caught a first fixture that did not actually breach. Testing the helper rather than the wiring is now the third instance of this shape in three sessions.

## 2026-08-18: Bound the exposure cap structurally rather than by pass count, and test guards by deleting them

**Why.** `loader.md`'s tilt table states a property of the output — "cap final exposure at 2× neutral to prevent runaway". The code delivered something else. `weights_for_groups` recomputed the over-cap set from scratch on every redistribution pass, and a holding clamped in pass N sits at exactly `EXPOSURE_CAP × neutral`, which the strict `>` test rejects. The clamped name therefore fell back into the free set and redistribution lifted it over the cap again. The loop oscillated rather than converging. This is the second time this function has shipped with code, docstring and test each describing a different property; the previous round fixed the *placement* of the clamp (raw multiplier vs post-normalisation) and left the *iteration* wrong.

Raising the pass count was not available as a fix. Convergence was non-monotone — on the pinned five-holding view, three passes (2.453×) is worse than two (2.413×) — so the shipped setting was not even locally optimal. It was also geometric rather than finite: over 20,000 random portfolios the worst needed 70 passes under the test module's own seed and 124 under another, so the figure is seed-dependent and the only safe reading is "unbounded". Any fixed constant has a counterexample, so the constant was never the parameter to tune.

Separately, two guards in the pre-push commit-message layer were correct and completely untested. Every stub scanner in the suite exited 0 or 1, so the tests proved the layer blocks on a *hit* and never that it blocks when the scan could not *run* — which is the family the incident that motivated the layer belongs to.

**Impact.**
- **The capped set is persistent.** Once clamped a holding stays at exactly `EXPOSURE_CAP × neutral` and never re-enters redistribution; the excess goes only to never-capped names. Each effective pass then adds at least one name to the capped set, so the loop terminates in at most one pass per holding, landing exactly at the cap rather than approaching it. `_CAP_PASSES` is removed and the bound is `len(weights) + 1` — structural, derived from the termination argument, not from a search.
- **The guarantee is now stated once, in three places that agree.** On return the weights sum to 1.0 and every holding with positive neutral weight satisfies `w[s] <= EXPOSURE_CAP * neutral[s]`. The docstring qualifies this to `neutral_w` summing to 1, the only kind the module builds, rather than claiming more than the code delivers.
- **Shapley efficiency is untouched.** It holds for any value function, so `Σ` per-tilt contributions `== model_active_bps` is preserved; the fix only changes what the value function returns.
- **No downside floor was invented.** `loader.md` specifies none, so −2 tilts still compound unbounded toward zero exactly as the table describes.
- **The pre-push layer's fail-closed paths are covered.** With the temp-file guard's `exit 2` removed the layer prints `BLOCKED` and then exits 0 — a push succeeds while the operator reads a block message. Narrowing the scanner exit-code check from `-ne 0` to `= 1` lets exit 2 through, the code `scan_commit_messages.py` returns on an unresolvable rev-range or a git failure. Neither guard changed; only the evidence that they work.

**Alternatives.**
- `[DROP]` **Raise `_CAP_PASSES` to a larger constant.** Rejected — convergence is geometric, so every constant has a counterexample, and it is non-monotone, so a larger constant is not even reliably better than a smaller one.
- `[DROP]` **Loop `while` any holding is over the cap, with a tolerance.** Rejected — it converges only asymptotically for the same reason, so it either spins on a pathological input or needs an escape hatch that reintroduces the bound.
- `[DROP]` **Clamp the raw multiplier before normalisation.** Already rejected in the previous round and recorded here so it is not re-proposed: the ratio that survives normalisation is `m / mean(m)`, which grows without limit as other holdings' multipliers fall. Measured at 3.37× with a pre-normalisation cap of 2.0.
- `[DROP]` **Assert on the loop's internals to pin the exact bound.** Rejected — the regression test uses a 14-holding view needing seven passes, so it kills small constants without asserting on private state. It does not pin the exact bound, and the test says so rather than implying otherwise. The justification for `len(weights) + 1` is the termination argument.
- `[DROP]` **Accept the green suite as evidence the previous fix worked.** Rejected as a method, not just as a conclusion. The 42 findings of the prior round and the four here were all found by deleting a guard and confirming a test fails. A passing suite never distinguished "the guard ran and allowed it" from "the guard never ran".

**Flip conditions.** (a) `loader.md` introduces a downside floor → the redistribution needs a symmetric lower clamp and the termination argument must be re-derived, since a two-sided constraint can cycle. (b) A portfolio family is found that forces the pass count to grow linearly with holding count → the `len(weights) + 1` bound stops being loose and its cost becomes worth measuring; directed search up to 26 holdings never exceeded seven passes. (c) The tilt table gains multipliers outside `0.50–1.50` → every measured figure in this entry is re-derived, since all of them sample that table.

**Known scope limits, recorded rather than glossed.** (a) The guarantee is `w[s] <= EXPOSURE_CAP * neutral[s] + 1e-12`; the slack is absolute while the quantity it bounds scales with `neutral`, so the ratio overshoot is `1e-12 / neutral[s]` and a contrived `neutral` of `1e-13` reaches 3.00× while still summing to 1.0. Unreachable from `neutral_weights`, which floors at `1/len(holdings)`, but the docstring no longer claims otherwise. (b) The cap governs the weights `weights_for_groups` returns. `active_return_bps` renormalises both legs over the price-covered set, so dropping a holding for missing data scales every surviving ratio by `nw_total/w_total` and can carry one above 2×. That path is pre-existing, is documented §3b behaviour with no coverage floor, and is NOT fixed here — flagged for a separate decision on whether the renormalised ratio counts as "final exposure".

**Verification.** 21 mutations were applied one at a time and reverted, against the shipped code and again against the fix. The exposure cap, tilt parsing, holdings-set merge, hook range/stdin/deletion/marker logic, public-bundle exclusion, `loader.md` attribution contract and symlink resolution are all covered — deleting any of them fails a test. Two survivors were equivalent mutations and are recorded as such. The cap fix was independently re-measured outside its own tests: the original counterexample lands at exactly 2.000000, and a 60,000-portfolio sweep (2–12 holdings, six compounding groups, a different seed from the suite's) gives worst exposure `2.000000000` with worst `|Σw − 1|` of `2.2e-16`. The defect itself was re-confirmed against pristine `HEAD` extracted via `git show`, run with bytecode writing disabled, to rule out a caching artifact.

One caveat worth recording. A same-size source mutation — swapping a digit, an operator, or a same-length identifier — can reuse a stale `.pyc` when rewritten inside one mtime second, and then reports SURVIVED while the original code ran. This produced one false result during the work and was caught only because a direct measurement disagreed with the mutation table. Mutation sweeps on Python must force invalidation; the size-neutral edits are exactly the ones most worth making.

## 2026-08-15: Make the render gate's fail-open audible, and enforce anchor-label agreement at PR time instead of by periodic review

**Why.** `render_gate.py` fails open by design: with no anchor match it returns the draft unchanged, so the gate can never destroy a report it cannot locate. The cost of that design was silence. A gated skill that renamed its title or first rendered section kept passing its own tests, kept producing output, and simply stopped stripping — pre-report scaffold reached the reader and the run looked clean from every angle. The proposed remedy was a recurring manual sweep of anchor labels. A calendar reminder is the weakest control available for a drift that a machine can detect exactly, and it decays the moment nobody runs it.

**Impact.**
- **The fail-open path writes one `[render-gate] WARN: no anchor for skill='<key>'; returned unchanged` line to stderr.** stdout stays byte-identical to the input, so the fail-open guarantee is unchanged and no draft is lost. Because a skill's final message is the command's stdout, the diagnostics had to go somewhere the reply cannot pick them up — stderr is that channel.
- **Every gated `SKILL.md` states the handling rule** next to its render step: the `WARN:` line is stderr, never part of the reply, never passed to the translate step, and it means the drafted opening drifted from the documented Output Format start. The rule is repeated per skill rather than referenced because the runtime loads one `SKILL.md` at a time; `parallax-conventions.md` §10.3 carries the same rule as the contract's owner.
- **`test_render_gate.py` checks the label/anchor/wiring contract in both directions.** Each registered skill's documented Output Format start label must appear in that skill's Output Format section and must be what `SKILL_ANCHORS` actually anchors on; separately, every `--skill` key wired in a `SKILL.md` must be registered, and every registered key must be wired by exactly the matching skill. A rename, an unregistered key, or an orphaned key now fails a test.
- **The suite runs in GitHub Actions** as its own step in `.github/workflows/evals.yml`, named explicitly rather than by widening the `skills/_parallax/scripts/` root (which would pull in the white-label `conftest.py` subtree and collide). An external pull request is therefore checked without a local gate run. `CONTRIBUTING.md` records the same-change rule for contributors.
- **`parallax-conventions.md` §10 now lists `desk-call-list`** among the gated skills and points at `SKILL_ANCHORS` as the registry, closing a prose/registry gap the bidirectional test would otherwise leave documented only in code.

**Alternatives.**
- `[DROP]` **Fail closed on no anchor.** Rejected — the gate would suppress a complete, correct report whenever an anchor regex lagged a legitimate rendering change. Losing the deliverable is strictly worse than shipping it with scaffold, and the warning plus the PR-time test address the detection problem without touching the output guarantee.
- `[DROP]` **Emit the warning on stdout as a comment line.** Rejected — stdout *is* the reply, so any marker becomes client-visible text in a white-labeled report.
- `[DROP]` **Periodic manual anchor-label review** (the shape originally proposed). Rejected in favor of the PR gate: the drift is exactly checkable, so a test catches it on the change that causes it rather than up to a review cycle later.
- `[DROP]` **Widen the CI `skills/_parallax/scripts/` root to cover the whole `_parallax` tree.** Rejected — it collects the white-label `conftest.py` subtree in the same process, the collision the per-root runner exists to avoid.

**Flip conditions.** (a) A gated skill legitimately needs to render output with no anchorable opening → the warning becomes noise for that skill and the anchor set, not the warning, is what changes. (b) `SKILL_ANCHORS` grows to cover skills whose `SKILL.md` lives outside `skills/parallax-<key>/` → the bidirectional test's path derivation needs a mapping instead of the name convention it assumes today.

**Verification.** `test_render_gate.py` gained coverage for the stderr warning (fail-open warns, stdout stays empty of it; an anchored draft warns not at all), for `desk-call-list`'s documented first section, and for the two bidirectional contract tests. The suite is wired into CI and into the local per-root gate runner, which discovers `skills/_parallax` automatically; the gate's test phase runs it on every push. `plugin/` was rebuilt from source after the conventions edit.

## 2026-08-15: Repair identity gates that compared against fields `analyze_portfolio` never returns, then close the normalizer's fail-open on contentless names

**Why.** `parallax-cio-letter-prep` and `parallax-scenario-analysis` each fetched a `get_company_info` ground-truth oracle and cross-checked it against a peer-rollup field in `analyze_portfolio` — a field that endpoint does not return, since it has no top-level identity field and no peer rollup at all. The comparison read nothing and every holding passed, silently. Fixing the comparison surfaced a second, independent bug one layer down: `normalize_company_name()` strips corporate-form tokens (`Inc.`, `Ltd`), so a name consisting of nothing else folds to the empty string, and two different contentless inputs both normalize to `""` and compare equal under `==` — the same "missing comparison treated as a pass" failure, arriving through the normalizer instead of through a dead field reference.

**Impact.**
- **Both skills now match `latest_holdings[].name` / `company_contribution[].name` against `get_company_info.name` by `ric`.** `parallax-conventions.md` §2 gained an `analyze_portfolio` row in its per-tool identity table, stating the field names and that a holding with no row in either block, or whose `get_company_info` call fails or returns empty, cannot be identity-checked and must be recorded UNCHECKED rather than passed.
- **`names_match(a, b)` returns `None`, not a bool, when either normalized side is empty.** An empty side is missing evidence, not evidence of divergence — returning `False` would flag a real holding as a wrong-company mapping, and returning `True` (bare `==`) was the original bug. Callers use `None` to record UNCHECKED, per the same disposition conventions §2 already required of an absent comparison. `normalize_company_name()` and `names_match()` live in `contract_validator.py` as the executable statement of the §2 step-2 prose.
- **`parallax-rebalance`, `parallax-portfolio-builder` and `parallax-thematic-screen`** picked up the same name-normalization step in their identity-flag instructions, so `Apple Inc` vs `Apple Inc.` stops reading as a mismatch across every consuming skill, not just the two that had the dead-field bug.
- **A five-skill batch this size risks fixing the same bug five different ways.** Doing it once in `contract_validator.py` and pointing every consumer at `parallax-conventions.md` §2 is why `normalize_company_name()` and `names_match()` are the only two functions any skill instruction cites.

**Alternatives.**
- `[DROP]` **Rescale/guard at each skill's call site instead of centralizing in `contract_validator.py`.** Rejected — five skills reading the identity table would each need the same guard re-derived from prose, and prose drift is exactly what produced the original dead-field bug.
- `[DROP]` **Return `False` for the undecidable case.** Rejected — flags a real, correctly-matched holding as a mismatch whenever its name-of-record happens to be a bare corporate-form token, which is a worse failure than the fail-open it replaces.

**Flip conditions.** (a) The Parallax MCP server starts returning a peer rollup or a top-level identity field on `analyze_portfolio` → the identity table's `analyze_portfolio` row and this workaround both simplify. (b) A tool response is observed with a name field that is present but genuinely blank for a real company (not just a corporate-form token) → `names_match()`'s empty-string heuristic needs a second guard, since blank-but-real and contentless-but-normalized-empty currently collapse to the same UNCHECKED disposition.

## 2026-08-05: A single locked commit path for the canonical house-view artifacts, with `audit.jsonl` carved out of every rename

**Why.** `parallax-load-house-view`'s save/extend/re-pair/clear paths each staged all four on-disk files — `view.yaml`, `prose.md`, `provenance.yaml`, and `audit.jsonl` — as `.tmp` siblings and renamed them into place. That is correct for the first three, which are whole-document replacements, and wrong for `audit.jsonl`, which is append-only by design: a rename swaps the file's inode out from under any reader (or the process's own `append_entry`) holding the old one, and the append logic then computes a fresh `chain_root` over what is now a truncated file rather than detecting the loss — `verify_chain` raises only when it sees *multiple* `chain_root` entries, not when it sees a plausible-looking single one sitting on top of history that no longer exists on disk. The defect was invisible at both the write and the verify layer at once. Fixing it by deleting one line from a rename list would still leave every content-writing step free-floating outside any lock, so the actual fix is a single commit function that owns the whole write, with the audit log structurally excluded from its capabilities rather than merely absent from today's call sites.

**Impact.**
- **`skills/_parallax/house-view/view_commit.py`** is now the sanctioned writer of `view.yaml` / `prose.md` / `provenance.yaml` **for `parallax-load-house-view`'s commit paths**. Read the scope literally: it is not a repo-wide invariant. `parallax-make-house-view`'s `maker.py` still writes all three directly with `write_text()` — it does hold the lock, it does not stage — and its migration is deferred (see the `[DROP]` on the maker below, and flip condition (a)). Bound the residual honestly. Maker's `save_view` wraps `_save_view_locked` in the same `view_transaction` `flock` on the same `.house-view.lock` that `commit_view` takes, and re-reads `parent_version_id` under it to raise `ViewChangedMidRun` on drift, so there is no lost-update window between a concurrent maker run and this commit — and it is precisely because maker already holds a transaction that it cannot simply call `commit_view`, which would re-acquire and deadlock. What maker lacks is staging: each artifact is written in place and `chmod`ed to `0600` afterwards, rather than staged as a `.tmp` sibling created at that mode and renamed. A crash or `ENOSPC` mid-write therefore leaves a truncated, unparseable `view.yaml` where a staged rename would have left the previous version intact, and a consumer that reads the view without taking the transaction (`view_status.py`) can observe the torn or briefly umask-permissive file. Maker's guard also covers `parent_version_id` only, with no row-vs-bytes assertion equivalent to `_validate_row_matches_bytes`. That residue — unstaged, not unlocked — is the real reason the migration is still worth doing. `audit.jsonl` is rejected by name from its `write`/`remove` key whitelist — not just omitted from what callers currently pass, but refused if anyone tries. `commit_view` acquires `audit_chain.view_transaction`'s `flock` and commits under it; `commit_view_locked` takes a `TransactionToken` (new frozen dataclass, yielded by `view_transaction`, scoped to a `view_dir`) for a caller that already holds the lock for another reason. `view_transaction` is not re-entrant, so `commit_view_locked` exists precisely to give a lock-holding caller a second entry point that does not attempt to re-acquire.
- **Validation order is the contract.** Token identity → write/remove key whitelist → audit-entry shape (`action`; `version_id` whenever writing; `view_hash` whenever `view.yaml` is written; `destination`+`reason` for `clear`) → identity guard (the caller's `expected_identity`, captured before the lock, re-checked against on-disk state under the lock — a `ViewChangedMidRun` on drift) → row-vs-bytes assertion (the row must describe the bytes it is about to witness) → stage-and-rename (`O_CREAT|O_EXCL|O_WRONLY`, `0600`, `fsync` before rename) → remove → append. Nothing touches the filesystem until every check upstream of it has passed.
- **Three failure modes, distinguished because their recovery differs.** `CommitRejected` — nothing written, safe to retry. `CommitPartiallyApplied` — a rename landed and a later step then failed; the rename cannot be undone (a compensating rename would race any reader that already observed the new bytes), so this is reported rather than silently absorbed into the same exit code as a clean rejection. `CommitWitnessLost` — every artifact committed but the audit row failed to append; recovery is hand-appending the row, never re-running the commit (that would duplicate the file writes).
- **Two residual gaps closed as a side effect.** `--clear` now archives all three artifacts to `.archive/<view_id>-<version_id>/` before committing the removal — the row's `destination` field is required, and a row asserting a move that never happened is a false statement in a record kept for seven years — and it removes `provenance.yaml` alongside the other two. Note which direction `audit_export.py` fails in: it raises when `provenance.yaml` is *missing*, not when it is present. Leaving a cleared view's provenance behind therefore risked a later export bundling a prior view's evidence as if it were current; removing it makes that export fail loudly instead, which is the correct outcome for a view that no longer exists. Separately, `--extend` and `--re-pair` now write an audit row (previously neither did, so a chain built entirely from extend/re-pair activity would show no history for it at all).
- **A stdin-JSON CLI** (`python3 -m view_commit --mode {save,extend,re-pair,clear}`) lets the loader's prose invoke the entire commit in one subprocess instead of open-coding staging, so there is exactly one implementation of the stage/rename/append sequence rather than one canonical version plus however many call sites reimplement it slightly differently.

**Alternatives.**
- `[DROP]` **Trim only `audit.jsonl` from the rename table.** Rejected — it removes today's visible symptom but leaves every prose-driven write to `view.yaml`/`prose.md`/`provenance.yaml` outside any lock at all, which reads as fixed while the actual hazard (uncoordinated writes to the canonical artifacts) is untouched.

## 2026-08-03: Land the agent hardening upstream where it survives, and make the bundle build repo-agnostic instead of repo-specific

**Why.** Most of this batch was first written downstream, in a distribution that regenerates its skill copies from this repo. A fix that lives only downstream is reverted by the next regeneration, so the only way to make it stick is to land it here — which is also where it belongs, since every exposure is in this repo's code. Four of them. (1) URL extraction reached the network through `scrapling` / `defuddle` / `requests` with no destination policy at all. A brand-guide URL is operator-supplied and the logo/favicon URLs are harvested from the fetched page, so both were a plain SSRF surface: cloud metadata endpoints, loopback admin panels, `file://` for the asset download. Three fetchers also meant three code paths to audit and no single seam a test could patch. (2) `trusted_keys.json` ships a test kid so an auditor can verify the signing round-trip on a fresh clone — and nothing stopped a production verify from accepting a manifest signed with it. (3) The stress and judge audit race guards compared `view_hash`, which covers tilts and excludes only, so a re-save that mints a fresh `version_id` over identical tilts passed the guard and the audit row attached to a version that was never the one tested; the two skills had additionally open-coded the same compare and already drifted on which fields they cited. **Impact.**
- **One fetch path, validate-then-pin.** A stdlib `urllib` pipeline rejects non-HTTP(S) schemes, embedded credentials, and any hostname whose resolution includes a non-public address; the addresses that passed are then pinned for the TCP dial, environment proxies are disabled, redirects are re-validated before their body is read, and reads are capped. `download_public_url()` puts asset downloads through the same policy. Rejection is a distinct `UrlNotPublicError` so the extractor can tell a refused destination from an unrelated `ValueError` further down.
- **Provenance keeps the query's shape and none of its contents.** The persisted `metadata.source.reference` keeps the parameter names that identify the page and redacts *every* value to `REDACTED` — there is no key list and no value is ever inspected. Pairs with a blank value are dropped instead of redacted, because `?flag` and `?<opaque-secret>` are indistinguishable after parsing and a key-preserving scheme would persist the second one verbatim. Two separate things were being conflated under one blanket rule: credentials live in userinfo (still dropped outright), while the query carries page identity that a blanket blank throws away. Recording the shape recovers that identity without offering full re-fetchability, which is deliberately not on the table — the operator has the original URL. Non-`str` input is rejected before `urlsplit()`, which accepts `bytes`/`None` without raising.
- **Test-only keys are denied by default.** `KeyTestOnly` at verify time, `allow_test_keys=True` (CLI `--allow-test-keys`) for harnesses, threaded through the cache and the load orchestrator. The auditor-facing round-trip survives; the production trust does not.

**Alternatives.**
- `[DROP]` **Keep `scrapling` / `defuddle` and put a destination check in front.** Rejected. PDF / PPTX / DOCX export and wizard mode already cover the intranet case, and `edge-cases.md` routes the operator there.
- `[DROP]` **Keep blanking the whole query string in the persisted provenance URL.** Rejected. It reads as the conservative choice but costs the reference its page identity — `?locale=en-GB&v=2024` recorded as a bare path resolves to a different or ambiguous page on re-extraction, which is the one job provenance has. The mirror-image alternative, `[DROP]` **keep the query wholesale**, is rejected for the original reason: this string is persisted into the draft, and query strings routinely carry `api_key` / `token` / `signature` values. Keeping the names and redacting every value satisfies both.
- `[DROP]` **Redact only the values whose key looks like a credential.** Rejected, and this one shipped briefly before being replaced. A denylist that fails open is the wrong shape for a control whose failure mode is a persisted credential, so there is no list: the value is the thing that must never survive, and the key is not evidence about it.
- `[DROP]` **Remove the test kid from `trusted_keys.json`.** Rejected. Its presence is what lets an auditor verify signing on a fresh clone, which is a compliance feature, not an oversight. Denying it at verify time keeps the audit path and removes the trust.
- `[DROP]` **Fold `view_id` / `version_id` into `view_hash` and keep comparing one value.** Rejected. `view_hash` is a published content identity recorded in audit rows and exports; redefining it would invalidate every hash already written. - `[DROP]` **Let `effective_plugin_skills()` skip any missing skill silently.** Rejected — that is precisely the failure this batch exists to fix. Only names declared optional may be absent; everything else is a typo or an un-updated rename and fails the build.

## 2026-08-02: Attribute a metered call by MCP namespace, and report the undecidable ones instead of guessing

**Why.** The derived token meter has to answer "is this call Parallax's?" for every tool call in a transcript, and both ways of inferring it from the tool *name* fail silently, in opposite directions. Matching on a namespace containing "parallax" undercounts a connector mounted off-brand: every call bills zero with an empty `unknown_endpoints`, which reads as a healthy free run rather than a broken meter. Falling back to the bare endpoint name fixes that but bills another server's colliding tool to the client — not hypothetical, since `submit_feedback` is not a name unique to Parallax among installable connectors. The mistake common to both is treating a tool name as proof of which server served it.

**Impact.**
- **Allowlist, not blocklist.** A Parallax endpoint always arrives MCP-namespaced, so a name with no namespace cannot be one. `estimate()` allowlists on the namespace and ignores everything else structurally; the hand-maintained harness-tool blocklist is deleted, not extended. That list was the same unfixable-signal failure `KNOWN_UNPRICED` exists to prevent, relocated into blocklist drift — a harness tool nobody remembered to add would have landed in `unknown_endpoints` and degraded runs permanently.
- **A third class.** A known endpoint name under an unrecognised namespace is `ambiguous`: billed to nobody, reported in `RunRecord.ambiguous_endpoints`, and the run degrades. Degrading is the point — the derived total is of unknown accuracy, so it must not pool into an aggregate presented as a measured client bill.
- **An operator escape hatch, in both directions.** Unlike `KNOWN_UNPRICED`, ambiguity is resolvable — but only if the operator can say *which* of the two things the namespace is. `PARALLAX_MCP_ALIASES` declares it the connector under an off-brand mount, and its calls start billing; `PARALLAX_MCP_FOREIGN_NAMESPACES` declares it a different server whose tool name merely collides, and its calls are ignored. Only one variable would force a foreign server to be declared a Parallax alias to silence the degrade, which starts billing the client for another server's calls. Both documented in `evals/README.md`.
- **Both live aliases bill.** The namespace check stays a substring match because transcripts carry more than one Parallax connector alias; an exact-match allowlist on one would silently drop the other's calls from the derived bill.

**Alternatives.**
- `[DROP]` **Namespace-only match, no ambiguous class.** Silently zero-bills an off-brand connector and is indistinguishable from a genuinely free run — the failure mode is invisible, which is the worst property a meter can have.
- `[DROP]` **Bare-name fallback when the namespace is unrecognised.** Misattributes a foreign server's colliding tool onto the client's invoice. A wrong bill is worse than a withheld one.
- `[DROP]` **Keep extending the harness-tool blocklist.** Correct only until the harness gains a tool, with no signal when it does.

**Flip conditions.** (a) The connector ships a stable server identifier in the transcript that survives renaming → attribute on that and retire the substring match. (b) `ambiguous_endpoints` shows up routinely in a deployment's runs → that namespace belongs in `PARALLAX_MCP_ALIASES` or `PARALLAX_MCP_FOREIGN_NAMESPACES` depending on which server it actually is, not in a widened default heuristic.

## 2026-05-25: Halal-screen concentration sanity-check gated on N≥8 compliant holdings

**Forward integration:** If production data shows the false-positive rate diverging from the assumption (e.g., real Shariah books with N=10-12 still hitting natural concentration), retune the cutoff. ## 2026-05-24: Judge bundle-name nonce — silent report overwrite under sub-second concurrent runs

**Why:** E2E concurrency tests (`tests/test_e2e_concurrency.py`, added 2026-05-24) surfaced that two judge runs against the same view within one wall-clock second silently overwrote each other's report bundle. The bundle name at `judge.py:614` was `{judged_version_id}-{seconds-precision timestamp}` — colliding for sub-second back-to-back runs. Audit chain was safe (`audit_chain.append_entry` uses `fcntl.flock(LOCK_EX)` per audit_chain.py:193) so audit.jsonl preserved all rows, but the bundle directory (which is the ONLY home for `report.md`, `report.json`, `mcp_responses.jsonl`, `audit_entry.json`) silently overwrote on the second write. Production manifestation: cron-fired auto-on-load drift check completing in the same second as an operator-triggered `/parallax-judge-house-view` → operator opens what they think is their report and gets the cron's, with no warning anywhere.
**Impact:** `judge.py:614` bundle_name now appends a 6-char `uuid.uuid4().hex[:6]` nonce: `{version_id}-{timestamp}-{nonce}`. Probability of nonce collision per pair of same-second runs ≈ 6e-8 (16.7M possibilities; was 1.5e-5 at 4 chars before code-reviewer flag — initial DECISIONS draft said 1.5e-9 which was mathematically wrong). Operationally negligible for production traffic shape (a few judge runs per day per client; even at 100/sec the birthday-bound collision probability stays under 1e-4 per same-second cohort). Test `test_e2e_serial_judge_runs_produce_distinct_audit_rows_and_reports` upgraded from xfail tripwire to passing assertion. Total tests: 329 passing + 1 remaining xfail (maker calibration tripwire above).
**Forward integration:** None — fix is self-contained. Bundle path consumers (none today; the path is opaque to callers via `JudgeResult.report_dir`) get a slightly longer path with no semantic change.
**Out of scope:** Same nonce pattern could be added to the maker's view-archive directory if we ever observe a similar collision there — not surfaced by current tests, defer.
**Alternatives:** [DROP] **4-char nonce (initial fix)** — rejected after code-reviewer flagged the math: 4-char = 65,536 possibilities → ~1.5e-5 collision per pair → not operationally safe given `render_judge.write_report_bundle` uses `mkdir(exist_ok=True)` (silent overwrite on collision). [DROP] **4-char nonce + collision-retry guard** — rejected; cleaner to widen the keyspace than add retry logic and an `if exists` branch. [DROP] **Switch to microsecond-precision timestamps without a nonce** — rejected; microseconds still race under heavy load, and the nonce gives stronger collision protection at negligible cost. [DROP] **Add file locking around bundle directory creation** — rejected; locks the wrong abstraction; the issue is name collision not write race. [DROP] **Refuse to start a judge run if a bundle dir with the same name exists** — rejected; would require pre-flight stat and surfaces as a user-visible error for what should be transparent disambiguation. **Flip conditions:** (a) Collision rate observed in production telemetry > 1 in 10⁶ → bump nonce to 8 hex chars. (b) Operator UX needs sortable bundle names → revisit naming scheme entirely (probably keep millisecond timestamp first, then nonce). Audit context: discovered by `test_e2e_concurrent_judge_runs_preserve_chain_integrity` in the concurrency test batch; nonce width tuned after code-reviewer review (4 → 6 chars).
